## 1. 한 문장

> 여행 전 필요한 비용을 근거 있게 계획하고, 여행자금을 준비하며, 실제 소비를 예산에 연결해 결산과 여행 유형으로 돌려주고, 그 결과를 다음 여행의 예산 추천에 다시 쓰는 **여행 금융 서비스.**

여행 일정 플래너도, 모임통장 관리 앱도, 가계부도 아니다. **중심 데이터는 거래내역이 아니라 여행 예산 계획이다.** (`CLAUDE.md` 2장)

## 2. 문제 정의

| Pain | 지금 사람들이 겪는 것 | TripPot 의 답 |
|---|---|---|
| 예산 설정 | 항공 · 숙박 · 식비를 따로 찾아 총액과 인당 금액을 감으로 정한다 | 목적지 · 일정 · 인원 · 스타일 기반 카테고리 예산 + AI 근거 상품 |
| 자금 준비 | 통장 잔액은 보여도 무엇까지 준비됐는지 모른다 | 목표금액 · 준비율 · 부족금액 · 가상 여행 금고 |
| 실제 소비 연결 | 실제 거래와 처음 세운 예산이 따로 논다 | 거래를 예산 카테고리 · 계획 항목의 실제값으로 연결 |
| 데이터 재사용 | 여행이 끝나면 다음 여행에서 처음부터 다시 계산한다 | 결산 · 여행 유형 · 다음 여행 개인화 추천 |

→ 상세: `01_서비스정의서_v2` §2

## 3. 핵심 사용자

- **Primary — 여행 총무형** (29세 직장인, 친구 3~4명과 정기 여행). 가격 검색 · 회비 결정 · 입금 확인 · 사후 정산을 혼자 맡는다.
- **Secondary** — 예산 상한형(쓸 돈을 먼저 정함) · 첫 해외여행형(항목과 적정 금액을 모름) · 목적형 리더(다이빙 · 공연 등 특수비용).

→ 상세: `01_서비스정의서_v2` §3

## 4. 핵심 루프

```text
여행 생성 → 예산 계획 → 자금 준비 → 실제 소비 → 예산 대비 비교
        → 결산 → 여행 유형 → 데이터 축적 → 다음 여행 개인화
```

- UI 는 여행 중심, 데이터는 개인 또는 모임에 쌓인다.
- **개인 여행은 DB 에 모임이 없는 여행이다** (`group_id = null`). 1인 모임 행을 만들지 않는다.
- **모임은 만드는 것이 아니라 생기는 것이다.** 초대 링크 → 참여 의사 → 여행장 수락 시점에 서버가 모임을 만들고 여행을 `PERSONAL → GROUP` 으로 전환한다.

→ 상세: `01_서비스정의서_v2` §5 · `10_여행초대정책_v2` · `11_모임정책_v2`

## 6. 기능 요구사항 요약

번호는 `03_요구사항정의서_v2` 의 REQ ID 다. 여기서는 **결정의 핵심만** 적는다.

| 영역 | 핵심 규칙 | 상태 |
|---|---|---|
| 여행 생성 | 신규 모임은 **이름만** 받는다. 멤버는 초대로만 늘어난다 | 구현 |
| 여행 상태 | 날짜로 자동 전환(출발일 → 여행 중, 종료 다음 날 → 종료). 수동 종료 버튼 없음. 서버 배치가 없어 **앱을 열어야** 전환된다 | 구현 (한계 기록) |
| 여행 정보 수정 | 일정 · 인원만. 목적지 · 모임은 못 바꾼다. 종료·결산 여행은 수정 차단 | 구현 |
| 예산 추천 | 규칙 기반 단가 + **AI 근거 상품 현지화**. AI 금액은 기준 대비 **±40% 안**에서만 반영 | 구현 |
| 예산 3칼럼 | `recommended_amount`(불변) · `personalized_amount`(개인화) · `planned_amount`(사용자 확정). **합치지 않는다** | 구현 |
| 가상 금고 | 항공 → 숙박 → 보험 → 액티비티 → 교통 → 식비 → 쇼핑 → 예비비 우선순위 자동 배분 | 구현 |
| 여행자금 | 연결 계좌 / 직접 입력 / 0원 **3택**. 직접입력 금액과 계좌 잔액을 **절대 합산하지 않는다** | 구현 |
| 거래 | 1 거래 = 1 카테고리. LLM 분류 결과는 `AUTO` 로 저장돼 '확인 필요' 에 잡히고 사용자가 최종 수정 | 구현 |
| 지출 입력 | 영수증 촬영 · 앨범 · 직접 입력 3종 | 구현 |
| 결산 | 종료 후 예상 vs 실제. 확정 시 카테고리 스냅샷 저장 | 구현 |
| 여행 유형 | **10종 · 규칙 기반 v1**(AI 미사용) | 구현 |
| 개인화 | 과거 결산 편차 × 추천값. **AI 가 `planned_amount` 를 직접 바꾸지 않는다** | 구현 |
| 커뮤니티 | 무료 팁만. 작성자는 **익명** 표시(쿼리가 이름·사진을 받지 않는다) | 구현 |
| 알림 | 알림센터 · 인앱 배너 · 안 읽음 점 · 매일 21시 지출 리마인드 | 구현 |

## 8. 데이터와 정책

- **예산 3칼럼을 합치지 않는다.** 추천 원본이 사라지면 "기본 추천이 맞았는지 · 개인화가 효과 있었는지" 를 영원히 측정할 수 없다. 이 프로젝트의 핵심 가설 검증이 여기 걸려 있다.
- **여행자금은 항상 단일 소스**(계좌 또는 수기)다. 수기 → 계좌 전환 시 수기 **입금** 거래는 soft delete 하고 계좌 잔액으로 대체한다.
- **거래는 원화 정수**로 다룬다. 환율 변환은 `[Future]`.
- 테이블 접근은 RLS 로 막는다. 앱은 `anon` 키만 쓰고, 관리자 권한 동작은 Edge Function 이 맡는다.
- MVP 금융 데이터는 전부 Mock 이지만, **Mock 인 것은 데이터 출처뿐**이고 예산·분석 로직은 실서비스 기준으로 설계한다.

→ 상세: `05_ERD_v7` · `16_여행멤버십_보안_v1` · `CLAUDE.md` 4장 · 11장

## 9. AI 사용

| 무엇 | 어디 | 가드레일 |
|---|---|---|
| 예산 근거 상품 현지화 | Edge Function `budget-products` | 금액은 규칙 기반, AI 는 ±40% 안에서만 |
| 거래 카테고리 분류 | Edge Function `classify-transaction` | 실패 시 규칙 fallback · 결과는 '확인 필요' |
| 영수증 읽기 | Edge Function `receipt-scan` | 사용자가 폼에서 확인 후 저장 |

- 앱에서 OpenAI 를 직접 부르지 않는다. 키는 Edge Function Secret 에 둔다.
- **AI 추천이 사용자 대신 확정하지 않는다.** 추천 + 근거 제시 → 사용자 확인/수정 → 사용자 최종 확정.
