## 1. 문서 목적 / 우선순위

이 문서는 정책을 **새로 정하지 않는다.** 이미 팀에서 확정한 정책을 한 곳에 모으고, 과거 흔적을 stale 로 표시해 **팀원과 AI 가 과거 정책을 최신 정책으로 오해하지 않게** 하는 것이 목적이다.

판단이 갈릴 때 순서:

```
1. 가장 최근 팀에서 명시적으로 확정한 정책          ← 이 문서
2. 최신 origin/develop 에 실제 merge 된 commit / PR
3. 이 문서 외 docs Source of Truth
4. 현재 실제 DB / schema / runtime code
5. migration / code comment
6. 과거 스펙 / prototype / 오래된 branch
```

과거 자료가 이 문서와 어긋나면 **과거를 지키려고 최신 정책을 바꾸지 않는다.** §15 에 폐기 목록이 있다.

## 2. 핵심 용어

| 용어 | 정의 |
|---|---|
| **여행장** | `trips.leader_user_id`. 여행당 **1명.** 참가 요청을 수락·거절하는 사람 |
| **ACTIVE 여행 멤버** | `trip_members.status = 'ACTIVE'` 이고 `user_id` 가 있는 사람. 여행장도 여기 포함된다 |
| **초대 링크** | `trip_invites` 한 행. `/invite/{token}`. 7일 유효 · 다인용 |
| **참가 요청** | `trip_join_requests` 한 행. 링크를 연 사람이 "참여할래요" 를 누른 결과. `PENDING` 으로 시작 |
| **수신자** | 링크를 열었지만 아직 ACTIVE 멤버가 아닌 사람. PENDING 이거나 요청 전 |
| **기존 여행** (모임 분기용) | **초대 대상 여행을 제외한**, 같은 모임의 다른 **유효 여행** 전부 (§9) |
| **유효 여행** | `status` 가 `DELETED` · `CANCELED` 가 아닌 여행. 현재 조회 코드의 기준과 같다 (§9-3) |
| **예정 인원** | `trips.headcount`. 예산 계산용. 실제 ACTIVE 멤버 수와 **별개** (§10) |

**모임장이라는 개념은 만들지 않는다.** 사용자 기능으로서 "모임 멤버 초대" 도 없다. 초대는 여행 단위 하나뿐이다.

`trips.owner_user_id` 는 **여행장 판정에 쓰지 않는다.** 그 칸은 "개인 여행의 주인" 이라는 기존 의미를 그대로 유지한다.

## 4. 초대 링크 생명주기 — POL-INV-014

### 4-1. 확정 정책

1. token 은 **DB 서버에서** 만든다. 앱이 만들지 않는다 (`get_or_create_trip_invite()` · §12)
2. 발급 시점부터 **7일** 유효. 만료 판정은 **서버 시각** 기준
3. 같은 링크를 **여러 사람이** 쓸 수 있다 (다인용 · 1회용 아님)
4. 그 여행에 **유효한 링크가 있으면 새 링크를 만들지 않고 그대로 재사용**한다
5. **다른 ACTIVE 멤버가 요청해도** 같은 유효 링크를 돌려준다
6. 기존 유효 링크를 **임의 재발급으로 즉시 무효화하지 않는다**
7. `expires_at` 이 지난 **이후에만** 새 token 이 생성된다
8. 새 token 은 그 시점부터 다시 7일
9. `created_by` = 그 token 을 **최초 생성한** ACTIVE 멤버. 마지막에 공유한 사람이 아니다
10. 동시에 여러 명이 요청해도 **유효 링크는 하나** — RPC 안에서 `trips` 행을 잠가 직렬화한다

### 4-2. invariant

> **하나의 여행에는 동시에 쓰는 유효한 초대 링크가 하나다.**

```
파리 여행 → token X (7일)
  A 공유 → X   B 공유 → X   C 공유 → X     같은 링크
  수신자 여러 명 → 모두 X 로 참가 요청 가능
7일 경과 → X 만료 → 그 이후 첫 요청에서 token Y → 다시 7일
```

### 4-3. `expires_at` 과 `revoked_at`

| 칼럼 | 현재 정책 |
|---|---|
| `expires_at` | 정상 7일 만료. **링크 생명주기는 전적으로 이 칼럼 기준** |
| `revoked_at` | **MVP 정상 흐름에서 사용하지 않는다.** RPC 는 `revoked_at is null` 인 행만 재사용하지만, 이 값을 **채우는 경로가 현재 없다.** 별도 강제 폐기 기능은 현재 확정 범위가 아니다 |

### 4-4. headcount 와 링크

**ACTIVE 멤버 수가 `headcount` 에 도달해도 token 을 만료·폐기하지 않는다.** 링크는 그대로 유효하고, **추가 승인만 제한**한다 (§10).

## 5. Sender flow — 여행 멤버 초대하기

```
여행준비홈 → 설정 → 여행 정보 수정 → [여행 멤버 초대하기]
  → get_or_create_trip_invite(tripId)      ← RPC. 유효 링크가 있으면 그것을 받는다
  → /invite/{token} 링크 조립
  → 초대 메시지 조립 (§13)
  → INV-01 공유 시트 → OS Share Sheet
  → 사용자가 카카오톡 / 메시지 / 기타 앱 선택
```

- **ACTIVE 멤버면 누구나** 이 flow 를 탈 수 있다. 여행장 여부로 막지 않는다
- 앱은 `trip_invites` 에 **직접 INSERT / UPDATE 하지 않는다** (GRANT 회수됨)
- 링크 발송 시점에 **모임을 만들거나 여행을 옮기지 않는다** (§9-4)

---

## 6. Receiver flow — 링크를 연 사람

```
/invite/{token}
  → signedOut 이면 로그인 → 같은 경로로 복귀
  → server-side 에서 token 검증 (현재 방향: Edge Function · service_role SELECT)
  → preview 표시 (§11 최소 정보)
  → [참여 요청] → trip_join_requests PENDING
  → 여행장 승인 대기
```

- 수신자는 아직 ACTIVE 멤버가 아니므로 **`trip_invites` 직접 SELECT RLS 를 열지 않는다**
- token 검증은 **server-side 경로**에서만 한다. 앱이 `trip_invites` 를 token 으로 조회하지 않는다
- 링크를 열었다고 멤버가 되지 않는다. **참여 요청 → 여행장 승인 → 참여 확정** 이다

## 7. Join Request — `trip_join_requests`

| 상태 | 의미 |
|---|---|
| `PENDING` | 요청됨. 여행장 판단 대기 |
| `ACCEPTED` | 수락됨. membership 반영 완료 |
| `REJECTED` | 거절됨 |
| `CANCELED` | 요청자가 취소 |

- 같은 여행에 **대기 중인 요청은 1인 1건** (`unique (trip_id, user_id) where status = 'PENDING'`)
- PENDING 사용자는 승인 전 **여행 홈의 민감 정보를 볼 수 없다**
- **PENDING 요청 수는 ACTIVE 멤버 수에 포함하지 않는다** (§10)
- LEFT 였던 사람도 새 링크로 다시 요청할 수 있다. 재참여는 확정 정책이다

## 8. 승인 / 거절 — 여행장만

- 수락·거절은 **여행장만** 한다
- 수락 **직전**에 `activeMemberCount < headcount` 를 **다시 확인**한다. 넘으면 수락을 막는다 (§10)
- 수락 시 §9-4 의 모임 처리가 **이 시점에** 실행된다
- 거절 사유는 묻지도 전달하지도 않는다 (POL-INV-051)
- 거절 기록은 같은 링크로의 재요청 차단에 쓴다

## 9. 모임 분기 — 최신 핵심 정책

### 9-1. "기존 여행" 의 최신 정의

> **현재 초대 대상 여행을 제외한, 같은 모임에 속한 다른 유효 여행 전부.**

다른 여행의 `status` 가 `PLANNING` 이든 `TRAVELING` 이든 `SETTLED` 든 **판정에 영향을 주지 않는다.** 하나라도 있으면 "기존 여행 있음" 이다.

### 9-2. 폐기된 과거 기준

- ❌ "SETTLED 여행이 1개 이상 있는가"
- ❌ "결산 완료 이력이 있는가"
- ❌ "여행중(TRAVELING) 또는 지난 여행(ENDED · SETTLED) 이 있는가" (non-PLANNING 기준)

### 9-3. 유효 여행에서 제외되는 상태

현재 조회 코드는 `DELETED` · `CANCELED` 를 일관되게 제외한다.

```ts
// lib/supabase/queries/trips.ts:57 · groups.ts:206 · funds.ts:451 · personalization.ts:65
.not('status', 'in', `(${TRIP_STATUS.DELETED},${TRIP_STATUS.CANCELED})`)
```

**따라서 모임 분기에서도 `DELETED` · `CANCELED` 는 "기존 여행" 에 세지 않는 것이 현재 코드와 일치한다.** `CANCEL_PENDING`(취소 요청 진행 중)은 아직 취소된 것이 아니므로 유효 여행으로 본다 — 단, 이 한 줄은 코드 기준의 정리이며 취소 기능 담당과 별도 확인이 필요하면 §16 에 남긴다.

### 9-4. 승인 시 모임 처리 (수락 시점에 실행)

| 수신자 상태 | 처리 |
|---|---|
| 이미 현재 모임의 ACTIVE 멤버 | `group_members` 변화 없음 → **target trip 에만** ACTIVE 로 참여 |
| 모임 멤버 아님 + **기존 여행 없음** | 기존 모임에 ACTIVE 로 추가 **+** target trip 에 ACTIVE 로 추가 |
| 모임 멤버 아님 + **기존 여행 하나라도 있음** | **새 모임 생성** → **target trip 1건만** 새 모임으로 **이동** → 기존 다른 여행들은 이전 모임에 그대로 → 수신자는 새 모임 + target trip 에 참여 |

**새 "여행 row" 를 복제하는 것이 아니다. 기존 target trip 자체가 새 모임으로 이동한다.**
`fund_sources` · `transactions` · 예산 등 **여행 단위 데이터는 target trip 과 함께 그대로 유지**된다. 별도 이관 로직을 만들지 않는다.

### 9-5. 실행 시점

- 링크 **발송 시점**에는 모임을 만들지도, 여행을 옮기지도 않는다
- INV-05 에서 새 모임 이름을 받으면 **`trips.pending_group_name` 에 저장만** 한다
- 실제 새 모임 생성 + target trip 이동은 **여행장이 ACCEPT 할 때** 실행한다
- 거절 · 요청 취소 · flow 종료 시 **아직 새 모임은 생성되지 않은 상태**여야 한다

**`pending_group_name` 정리 규칙 — 현재 근거는 DB 칼럼 주석뿐이다.**
> `수락 시 소비하고 null 로 되돌린다. 거절·만료 시에도 null.` (`20260910000001` 칼럼 comment)

이를 실행하는 **앱 코드는 아직 없다.** 승인 flow 구현 시 이 규칙을 따른다.

## 10. headcount — 예정 인원

| 정책 | 내용 |
|---|---|
| 의미 | `trips.headcount` 는 **예산 계산용 예정 인원.** 실제 ACTIVE 멤버 수와 별개 |
| 자동 증가 | ❌ 참가 승인으로 headcount 를 **올리지 않는다** |
| 예산 재계산 | ❌ 참가 승인으로 예산을 **다시 계산하지 않는다** |
| 화면 표현 | `"N명 예정 · M명 참여 중"` (`lib/trip/members.ts` `headcountLabel`) |
| 링크 | ACTIVE 수가 headcount 에 도달해도 **token 을 EXPIRED / REVOKED 처리하지 않는다** |
| 승인 제한 | `activeMemberCount >= headcount` 면 **추가 승인만 막는다** |
| headcount 상향 | 기존 유효 token 과 기존 PENDING 요청을 **그대로 다시 쓸 수 있다** |
| PENDING 집계 | PENDING 요청 수는 `activeMemberCount` 에 **포함하지 않는다** |
| 승인 직전 재확인 | 수락 시 `activeMemberCount < headcount` 를 **다시 확인**한다 |
| headcount 하향 | ACTIVE 수보다 작아져도 **기존 멤버를 자동 제거하지 않는다.** `4명 예정 · 5명 참여 중` 상태도 허용. 추가 승인만 막는다 |

> ⚠️ **"N명이 차면 링크 자동 비활성" 은 폐기됐다.** 현재 UI 문구에 남아 있다 (§16).

## 12. DB / RLS / RPC contract — 현재 실제 구현

**기준: PR #86 · `supabase/migrations/20260911000001_trip_invite_rpc.sql` · 원격 DB 적용 완료 (2026-09-11)**

### 12-1. `get_or_create_trip_invite(p_trip_id uuid)` — 링크 발급의 유일한 통로

```
returns table (invite_id uuid, token text, expires_at timestamptz)
security definer · search_path = public, pg_temp
grant execute → authenticated 만 (public · anon 회수)
```

함수 안에서 하는 일 (순서대로):

1. `auth.uid()` 없으면 42501
2. `select … from trips where id = p_trip_id for update` — **같은 여행의 요청을 직렬화** (다른 여행끼리는 서로 막지 않음)
3. 요청자가 그 여행의 **ACTIVE `trip_members`** 가 아니면 42501 — **여행장 여부는 보지 않는다**
4. `revoked_at is null and expires_at > now()` 인 행이 있으면 **그것을 돌려준다**
5. 없을 때만 INSERT — `token = encode(extensions.gen_random_bytes(32), 'hex')`, `created_by = auth.uid()`, `expires_at = now() + 7 days`

`gen_random_bytes` 는 **`extensions.` 스키마 이름을 붙여** 부른다. Supabase 가 pgcrypto 를 `extensions` 에 두기 때문이며, `search_path` 를 넓히지 않는다.

`types/database.ts` 에 `Functions.get_or_create_trip_invite` 타입이 반영돼 있다.

### 12-2. `trip_invites` 권한

| 주체 | SELECT | INSERT | UPDATE | DELETE |
|---|---|---|---|---|
| `anon` | ❌ | ❌ | ❌ | ❌ |
| `authenticated` (ACTIVE 멤버) | ✅ RLS `trip_invites_select_active_member` | ❌ (GRANT 회수) | ❌ (GRANT 회수) | ❌ |
| `authenticated` (비멤버 · LEFT · PENDING) | ❌ | ❌ | ❌ | ❌ |
| `service_role` | ✅ (수신자 token 검증용) | ❌ (회수) | ❌ (회수) | ❌ (회수) |

- **`dev_open_all` 은 이 표에서 삭제됐다.** 다른 표는 그대로다
- INSERT · UPDATE · DELETE **정책이 없다.** 정책이 없으면 RLS 가 막는다. 발급은 RPC(security definer)가 한다
- `service_role` 은 RLS 는 우회하지만 **테이블 GRANT 는 우회하지 않는다.** 그래서 SELECT GRANT 가 필요했고, 쓰기 권한은 요청자 판정으로 회수했다

### 12-3. `trip_join_requests`

PR #86 은 이 표를 **건드리지 않았다.** `dev_open_all` 그대로이고, 수락 권한은 여행장으로 유지한다. 배포 전 `join_req_self_or_owner` 로 교체 예정 (`20260910000001` 하단 주석).

### 12-4. 과거 초안과 혼동 금지

| 위치 | 내용 | 상태 |
|---|---|---|
| `20260910000001` 하단 주석 `invites_owner` | 링크 발급·조회를 **여행장만** | **당시 배포 초안. 원격에 적용된 적 없음. PR #86 으로 대체됨** |
| `20260910000001:151` `-- 앱이 만들어 넣는다 (POL-INV-010)` | token 을 앱이 생성 | **폐기. RPC 가 생성** |

**마이그레이션 파일 본문·주석은 수정하지 않는다.** 스키마 이력이고, 원격 적용 이력과의 혼동을 막아야 한다. 해석 기준은 이 문서다.

### 16-4. 구현자가 지킬 것

- `trip_invites` 에 앱이 직접 쓰지 않는다. 발급은 **`supabase.rpc('get_or_create_trip_invite', { p_trip_id })`** 한 경로
- 수신자 화면에서 `trip_invites` 를 token 으로 직접 조회하지 않는다. **server-side 검증**만
- 승인 로직은 **수락 직전** headcount 를 다시 확인한다
- 링크 발송 시점에 모임·여행을 만들거나 옮기지 않는다
- 마이그레이션 주석과 이 문서가 다르면 **이 문서**
- 화면 문구에 "여행장만 초대" · "N명 차면 닫힘" · "새 링크 발급으로 무효" · "결산 이력" 이 남아 있으면 **STALE** 이다. 새 화면에 복사하지 않는다
