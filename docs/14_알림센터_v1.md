## 1. 정의

**알림센터는 "푸시 알림 목록"이 아니다.**
TripPot 에서 사용자가 알아야 하는 **중요한 여행·참여 상태 변화**를 나중에도 다시 확인하고, 필요하면 관련 행동으로 이어갈 수 있는 **통합 알림함**이다.

```
Domain Action (참여 요청 · 승인 · 거절 · 초대 열람 …)
      ↓
public.notifications  ← 논리적 알림의 Source of Truth (1 알림 = 1 행)
      ↓
      ├─ 알림센터 (/me/notifications · 목록 → 상세 → CTA)
      ├─ In-app Banner (앱 사용 중 · 앱 실행/복귀 시)
      └─ Remote Push (optional · future — 전달 채널일 뿐 알림이 아니다)
```

원칙
- Push 가 없어도 알림센터는 완전히 동작한다.
- Banner 를 놓쳐도 알림센터에는 남는다.
- 앱을 껐다 켜도 DB 알림은 그대로 다시 보인다.
- Push 실패·Banner 실패가 domain action 이나 알림 행 생성을 실패시키지 않는다.
- 알림 코드에 iOS/Android 조건을 넣지 않는다. 플랫폼 차이는 Push 자격(APNs/FCM)에만 있다.

## 2. Source of Truth — `public.notifications`

| 컬럼 | 의미 |
|---|---|
| `id` | 알림 id. Push payload 의 `notificationId` 와 같은 값 |
| `user_id` | **수신자**. 알림은 항상 한 사람에게 간다 |
| `type` | `NOTIFICATION_TYPE` (CHECK 로 잠김) |
| `title` · `body` | 발생 당시의 문구 **스냅샷**. 나중에 바뀌지 않는다 |
| `trip_id` | 관련 여행. 여행이 지워지면 null (FK SET NULL) |
| `data` (jsonb · null) | type 별 이동 문맥. §5 |
| `read_at` | 사용자가 실제로 확인한 시각. §7 |
| `created_at` | 발생 시각. 정렬·조회 window·retention 기준 |

- **생성 주체: SECURITY DEFINER RPC 만.** 클라이언트 INSERT 금지(§10). Edge Function 은 만들지 않는다.
- 알림 행은 **새 상태 변화가 실제로 일어난 순간에만** 1회 만든다. 멱등 반환(이미 PENDING 인 요청을 다시 돌려줌 등)에서는 만들지 않는다.
- 알림 생성 실패는 domain 트랜잭션을 깨뜨리지 않는다(예외 격리). 반대로 domain 이 실패하면 알림도 같이 롤백된다(같은 트랜잭션).
- 알림 설정(`users.notification_settings_json`)은 **알림 행 생성을 막지 않는다.** 중요한 이력은 항상 남긴다. 설정의 의미(Push·Banner 표시 여부)는 Push 정책과 함께 나중에 정한다. 이번에 기존 설정 UI 의미를 바꾸지 않는다.

## 3. MVP 범위 — 카테고리와 type

사용자 화면 필터 (raw type 을 보여주지 않는다):

| 필터 | 포함 type (앱 상수 `NOTIFICATION_CATEGORY` 로 관리 · DB category 컬럼 없음) |
|---|---|
| 전체 | 아래 전부 |
| 초대·참여 | `INVITE_RECEIVED` · `JOIN_REQUESTED` · `JOIN_ACCEPTED` · `JOIN_REJECTED` · `MEMBER_JOINED` |
| 멤버·권한 | `MEMBER_LEFT` · `OWNER_DELEGATED` |
| 여행 취소 | `CANCEL_REQUESTED` · `CANCEL_VOTE_AGREED` · `CANCEL_REJECTED` · `CANCEL_EXPIRED` · `CANCEL_WITHDRAWN` · `CANCEL_CONFIRMED` · `CANCEL_RESTORED` |

**현재 In-app 알림 범위에서 제외** (상수·CHECK 에는 남긴다. producer 없음. Remote Push 정책을 정할 때 다시 본다):
`FUND_GOAL_REACHED` · `TRIP_D7` · `SETTLEMENT_READY`

**`INVITE_SENT`** — "초대 링크 발송 → 초대받은 사람"으로 정의돼 있었으나 multi-use 링크는 발송 시점에 수신자를 알 수 없어 실제로 만들 수 없다. 값은 유지하되 **미사용**. 수신자용은 아래 `INVITE_RECEIVED` 를 쓴다(17 → 18종).

### 3-1. 1차 구현(vertical slice) — producer 까지

| type | 언제 (정확히 1회) | 수신자 | 알림센터 | Banner | 상세 CTA (현재 상태 기준) |
|---|---|---|---|---|---|
| `INVITE_RECEIVED` | 로그인한 사용자가 **VALID** 초대 링크를 열어 수신자로 식별된 첫 순간. 같은 (user, invite) 는 1회 | 링크를 연 사람 (ACTIVE 멤버·링크 발급자·이 invite 에 REJECTED 된 사람 제외) | 필수 | **안 띄움** (그 순간 이미 초대 화면을 보고 있다) | VALID+미요청 → [여행 초대 확인하기] · PENDING → "승인 대기 중" · ACTIVE → [여행 보기] · REJECTED/EXPIRED/REVOKED → 상태 안내, CTA 없음 |
| `JOIN_REQUESTED` | `request_trip_join` 이 **새 PENDING 행을 INSERT** 했을 때만 (멱등 반환·중복 클릭 분기 제외) | `trips.leader_user_id` (null 이면 생성 안 함) | 필수 | 필수 | PENDING → [참여 요청 확인하기] (`/trips/[tripId]/edit`) · ACCEPTED → "승인 완료" [여행 보기] · REJECTED → "처리 완료" |
| `JOIN_ACCEPTED` | `accept_trip_join_request` 가 요청을 ACCEPTED 로 바꿨을 때 (CASE A~D 공통) | 요청자 | 필수 | 필수 | [여행 보기] (`/trips/[tripId]`) · 그 사이 LEFT 면 "나간 여행" |
| `JOIN_REJECTED` | `reject_trip_join_request` 가 REJECTED 로 바꿨을 때 | 요청자 | 필수 | 필수 | 없음. 거절 사유 비노출(POL-INV-051) |

### 3-2. 2차 (인프라만 대응 · producer 는 후속 PR)
`MEMBER_JOINED` · `MEMBER_LEFT` · `OWNER_DELEGATED` · `CANCEL_REQUESTED` · `CANCEL_REJECTED` · `CANCEL_EXPIRED` · `CANCEL_WITHDRAWN` · `CANCEL_CONFIRMED` · `CANCEL_RESTORED`
— 나가기·위임·취소는 현재 앱 클라이언트가 직접 UPDATE 하므로(RPC 없음) producer 를 붙이려면 trigger 또는 RPC 화가 필요하다. 이번 PR 에 섞지 않는다.
`CANCEL_VOTE_AGREED` 는 소음이라 producer **제외 권장** 유지.

## 4. 문구 (2026-09-16 확정 — actor/inviter 이름 포함형)

- 문구는 **생성 시점에 title/body 로 스냅샷**한다(DB · Push 공통). 나중에 이름·여행지가 바뀌어도 알림은 그대로다.
- **여행 라벨 `tripLabel`**: `trips.destination` 이 있으면 `"{destination} 여행"` (예: `도쿄 여행`), 없거나 빈 문자열이면 `"이 여행"`. 문구 쪽에 다시 "여행"을 붙이지 않는다("도쿄 여행 여행" 금지).
- **사람 이름**: `users.name` (앱이 이미 표시 이름으로 쓰는 필드 · 새 필드 없음). null·빈 문자열이면 `"사용자"`. 이메일·연락처 등 다른 개인정보는 넣지 않는다.
- SQL producer 와 `lib/notifications/messages.ts` 는 **같은 문자열**을 갖는다. 맞추기 위한 과도한 공통화는 하지 않는다.

| type | title | body |
|---|---|---|
| `INVITE_RECEIVED` | 여행 초대를 받았어요 | {inviterName}님이 {tripLabel}에 초대했어요. |
| `JOIN_REQUESTED` | 여행 참여 요청이 도착했어요 | {actorName}님이 {tripLabel} 참여를 요청했어요. |
| `JOIN_ACCEPTED` | 여행 참여가 승인됐어요 | {tripLabel} 참여가 승인됐어요. |
| `JOIN_REJECTED` | 여행 참여 요청이 거절됐어요 | {tripLabel} 참여 요청이 거절됐어요. |

예: `사용자님이 도쿄 여행 참여를 요청했어요.` · `한나님이 이 여행에 초대했어요.`

## 5. 이동 문맥 `data` (jsonb)

- type 별로 **필요한 키만**, 문자열 값. 알 수 없는 키는 무시한다.

| type | data |
|---|---|
| `INVITE_RECEIVED` | `{ "inviteId", "inviterUserId" }` |
| `JOIN_REQUESTED` | `{ "requestId", "inviteId", "actorUserId" }` |
| `JOIN_ACCEPTED` | `{ "requestId", "groupId"? }` |
| `JOIN_REJECTED` | `{ "requestId" }` |

- **raw invite token 은 절대 저장하지 않는다.** 재진입은 `inviteId` + 서버 검증 RPC(`resolve_trip_invite_by_id` · `request_trip_join_by_invite`)로 한다. 서버는 "그 invite 의 `INVITE_RECEIVED` 알림을 가진 사람 / 그 invite 로 요청한 적 있는 사람 / 그 여행의 ACTIVE 멤버"에게만 응답하고, token 은 클라이언트로 내려가지 않는다.

## 6. 알림 상세와 상태 기반 CTA

- 목록 row 탭 → **상세**(`/me/notifications/[notificationId]`) → CTA → domain 화면. 바로 domain 으로 보내지 않는다.
- 상세는 title · body 전문 · 발생 시각 · 관련 여행 · **현재 상태** · CTA 를 보여준다.
- row 는 과거 사실이다. **CTA 와 상태 라벨은 눌렀을 때의 현재 domain 상태로 계산**한다 (앱 계층 `lib/notifications/resolveNotificationAction.ts` · type × 현재 상태 → `{ statusLabel, cta? }` · 플랫폼 무관).
- 이미 처리된 알림은 "승인 완료 / 처리 완료 / 만료됨" 등 현재 상태를 보여주고 과거 버튼을 그대로 두지 않는다. 여행이 사라졌으면(`trip_id` null) CTA 없음.

## 7. 읽음(`read_at`)

- **Banner 노출 ≠ 읽음.** Banner 가 떠도 `read_at` 을 찍지 않는다.
- `read_at` 은 사용자의 실제 확인 행동에서만: Banner CTA 탭 · 상세 진입 · (목록 row 탭 = 상세 진입).
- 처음 읽은 시각을 지킨다. 이미 읽은 알림은 다시 쓰지 않는다.

## 8. In-app Banner

| 상황 | 동작 |
|---|---|
| 앱 사용 중(foreground) 새 알림 행 INSERT | Supabase Realtime `postgres_changes`(`user_id = 나`) 로 받아 **즉시** 상단 Banner |
| 앱 최초 실행 · background → foreground 복귀 | unread 를 다시 조회해 이번 세션에 아직 안 보여준 최신 1건을 Banner (Realtime 누락 보완) |
| 같은 세션에서 같은 알림 | 반복 표시 안 함 — 메모리 `Set<notificationId>` |
| 프로세스 완전 종료 뒤 여전히 unread | 다음 실행에서 다시 뜰 수 있음 (MVP 허용) |
| Push 를 눌러 앱을 연 경우 (future) | Banner 로 반복하지 않고 상세/목적지로 이동 + Set 등록 |
| `INVITE_RECEIVED` | 생성 순간 초대 화면을 보고 있으므로 Banner 생략 (알림센터에는 기록) |

- 구독은 로그인 사용자마다 1개. 로그인/로그아웃/계정 전환 시 정리하고 다시 만든다.

## 9. 조회 · 보관 (2026-09-16 확정 — 90/365 안 폐기 → 365/730)

| 항목 | 정책 |
|---|---|
| 알림센터 조회 window | **최근 365일 (1년)** — `NOTIFICATION_CENTER_WINDOW_DAYS` |
| 페이지 | **30건** (`NOTIFICATION_PAGE_SIZE`) · **cursor 기반**(`created_at desc, id desc`) · 서버에서 자른다 |
| 필터 | **서버 측** `type in (카테고리 type 목록)` — 30건 받아 클라이언트에서 거르지 않는다 |
| 기존 `.slice(0, 30)` | **폐기** (2026-09-16 구현 완료) |
| 인덱스 | 기존 `(user_id, created_at desc)` 재사용. 실측 plan 상 필요하기 전엔 추가하지 않는다 |
| DB 보관(retention) | **730일 (2년)** — UI window 와 별개 |
| 정리 | pg_cron **하루 1회** (KST 03:00 = UTC 18:00) `created_at < now() - interval '730 days'` 행 hard delete. 개수 상한·"DB 가 찰 때" 방식은 쓰지 않는다 (예측 가능 · 사용자별 일관 · headroom) |
| 사용자 삭제 | 현재처럼 hard delete (되돌리기 없음). **730일은 사용자가 지우지 않은 알림의 최대 보관기간**이다 — 알림센터에서 본인 알림을 직접 지우면 730일 전에도 사라진다. retention cleanup(cron)과는 별개의 사용자 동작이다. `public.notifications` 는 사용자용 알림센터의 SoT 이지 감사 로그가 아니다 |

**왜 365일인가.** TripPot 의 한 바퀴(계획 → 예상 예산 → 자금 준비 → 여행 → 실제 지출 → 비교·회고 → 다음 여행 반영)는
수개월 이상 이어지고, 해외여행은 수개월~1년 전부터 준비한다. 90일은 그 사이의 초대·승인·취소 이력을 잘라 버린다.
MVP 에서는 "진행 중인 여행의 알림은 기간과 무관하게 표시" 같은 예외를 두지 않고, **최근 1년**이라는 단순하고 예측 가능한
window 하나로 간다. 1년 넘게 준비하는 active trip 의 과거 알림이 중요하다는 근거가 실제 사용에서 생기면 그때 active-trip
예외를 별도로 검토한다.

**UI 365일 ≠ DB 730일.** 조회 window 밖의 행은 화면에 안 보일 뿐 DB 에 남고, 730일이 지난 행만 cron 이 지운다.

## 10. 보안 (외부 사용자 테스트 전 필수)

| 대상 | 정책 |
|---|---|
| SELECT / UPDATE / DELETE | `user_id = auth.uid()` |
| INSERT | 클라이언트 금지 — 정책 없음 + `anon`/`authenticated` INSERT GRANT 회수 |
| 생성 | SECURITY DEFINER RPC 만 |
| Realtime | 위 SELECT 정책이 그대로 적용된다(정책 없으면 이벤트도 안 온다) |
| `dev_open_all` | 알림센터 구현·앱 query 정리 후, 최종 2계정 E2E **전에** 제거. 별도 migration(롤백 쉬움) |

## 11. Remote Push 와의 관계 (future)

- Push 를 DB 알림과 **별개 알림으로 만들지 않는다.** payload: `{ "notificationId", "type", "tripId" }` (문자열).
- `notificationId` 가 있는 Push = 같은 논리적 알림 → 기기 보관함(PushInbox)에 두 번째 행을 만들지 않고 상세로 연결한다.
- `notificationId` 가 없는 Push(테스트·generic·legacy)만 PR #97 PushInbox 가 fallback 으로 보관한다.
- 토큰 저장은 `1 user : N devices`(`user_push_tokens`)로 열어 둔다. 이번 범위 아님.

## 12. 이번 범위 밖

FUND/TRIP_D7/SETTLEMENT producer · 2차 type producer · Remote Push 발송 · 토큰 저장 · Edge Function sender · 알림 설정 의미 변경 · pending route 영구 저장(로그인 도중 프로세스 종료 시 유실 — 실측 후 보강).
