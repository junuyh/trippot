## 1. 서비스 정의

> 여행 전 필요한 비용을 근거 있게 계획하고, 여행자금을 준비하며, 실제 소비를 예산에 연결해 결산과 여행 유형으로 돌려주고, 그 결과를 다음 여행의 예산 추천에 다시 쓰는 **여행 금융 서비스.**

TripPot은 단순 여행 일정 플래너나 모임통장 관리 앱이 아니다. 사용자가 `얼마가 필요한지 계획하고 → 얼마나 준비됐는지 확인하고 → 실제로 어디에 썼는지 연결하고 → 다음 여행에 재사용`하도록 돕는다.

지금의 TripPot 을 한 문단으로 적으면 이렇다. 카카오·구글·이메일로 로그인해서, 13개 해외 목적지 목록에서 도시를 고르고 일정·인원을 넣으면, 규칙 기반 단가에 AI가 현지 상품명·금액을 붙인 카테고리별 추천 예산이 먼저 나온다. 사용자는 근거 상품을 켜고 끄고 예비비 비율을 고르며, 직접 입력으로 바꿀 수도 있다. 여행자금은 Mock 계좌 연결·직접 입력·0원 중 하나로 시작하고, 이후 여행 준비 홈에서 예산 상세·자금 입출금·영수증 스캔·AI 거래 분류를 쓴다. 출발일이 되면 자동으로 "여행 중"이 되고 매일 21시 지출 리마인드가 오며, 종료일 다음 날 자동으로 결산으로 넘어가 정산 카드/PDF 공유와 9종 여행 유형 결과까지 나온다. 다음 여행에서는 지난 결산 편차가 개인화 추천으로 반영된다.

> **🔁 변경 (v1 → v2)**
> - **이전(v1)**: "여행 전 필요한 비용을 계획하고 여행자금을 준비하며, 실제 소비 경험을 다음 여행의 더 나은 예산으로 연결하는 여행 금융 서비스."
> - **문제정의**: v1 문장은 유효하지만 결산·여행 유형·개인화 추천이 실제로 구현된 지금, 소개서에 쓰기엔 "무엇을 돌려주는가"가 빠져 있다.
> - **의사결정**: 18 §1-1 의 소개서용 문장으로 확장. 2026-09-18 · `18_서비스비교정리.md` §1 · §1-1. 핵심 뜻(계획 → 준비 → 소비 연결 → 재사용)은 그대로다.

## 3. 핵심 사용자

### Primary — 김지수 / 29세 / 직장인 / 여행 총무형

친구 3~4명과 정기적으로 여행하며 가격 검색, 엑셀 정리, 인당 회비 결정, 입금 확인, 여행 후 정산을 담당한다.

**Pain**

- 회비 금액의 근거가 부족하고 부족하면 다시 걷어야 한다.
- 현재 자금으로 무엇까지 준비됐는지 파악하기 어렵다.
- 여행 후 초과 지출 원인을 정리하지 않고 다음 여행에서 다시 계산한다.

**Needs**

- 전체 예상경비와 인당 목표금액
- 항목별 준비 상태
- 선택형 멤버 납부 현황
- 예상 vs 실제 결산
- 과거 소비 기반 다음 여행 추천

### Secondary Persona

| 유형 | 핵심 상황 | 주요 Needs |
|---|---|---|
| 예산 상한형 | 사용 가능한 예산을 먼저 정함 | 입력 예산과 추천 예산 비교, 부족/여유 확인 |
| 첫 해외여행형 | 비용 항목과 적정 금액 자체를 모름 | 추천 총액, 필수 카테고리, 기본 팁 |

## 4. 핵심 가치

1. **근거 있는 예산:** 여행지·일정·인원·스타일을 바탕으로 예상비를 제공한다. 금액은 규칙 기반 단가로 계산하고, 그 위에 AI(Edge Function `budget-products`)가 카테고리별 **근거 상품명·금액을 현지화**해 붙인다. AI 금액은 규칙 단가 대비 ±40% 가드레일 안에서만 반영된다. 사용자는 근거 상품을 체크박스로 켜고 끄며 예비비 비율을 고른다.
2. **선택 가능한 자금 관리:** 연결된 계좌(Mock) · 직접 입력 · 0원 시작의 3택을 지원한다. 신규 계좌 개설은 생성 흐름 밖(여행 홈)이다.
3. **준비 상태 가시화:** 현재 자금이 여행 계획의 어느 항목까지 준비됐는지 보여준다. 배분은 항공 → 숙박 → 보험 → 액티비티 → 교통 → 식비 → 쇼핑 → 예비비 우선순위로 자동 채운다.
4. **예산 중심의 실제값 연결:** 거래내역은 예산 계획을 채우는 실제값이다. 영수증 스캔(Edge Function `receipt-scan`)으로 거래를 입력할 수 있고, 카테고리는 LLM(Edge Function `classify-transaction`)이 분류한 뒤 규칙 fallback 과 사용자 수정을 거친다.
5. **재미있는 여행 결과:** 여행 종료 후 예산과 지출을 바탕으로 대표 유형과 여러 특성을 보여준다. 유형은 9종 · 규칙 기반이다.
6. **반복할수록 나아지는 추천:** 첫 여행부터 개인화에 사용하고 누적 데이터로 근거를 확장한다.

> **🔁 변경 (v1 → v2)**
> - **이전(v1)**: 1 · "여행지·일정·인원·스타일을 바탕으로 예상비를 제공한다" / 2 · "기존/신규 계좌, 직접 입력, 0원 시작을 지원한다" / 4 · 거래 입력 방식 언급 없음 / 5 · 유형 개수·산출 방식 언급 없음.
> - **문제정의**: ① 항공만 AI 로 하면 "근거 있는 예산"이 보이지 않았고, AI 금액을 그대로 쓰면 시연이 흔들렸다(18 §2-13). ② 생성 흐름에서 계좌 개설까지 하면 이탈한다(18 §2-16). ③ Mock 분류는 시연에서 틀린 카테고리만 보여줬고, 여행 중 수기 입력의 가장 큰 마찰이 영수증이었다(18 §4-14 · §4-15). ④ 결산 데이터가 쌓이기 전이라 유형은 규칙으로 산출한다(18 §5-6).

## 5. 서비스 중심축

```text
여행 생성
→ 여행 예산 계획
→ 여행자금 준비
→ 실제 소비
→ 예산과 실제 비교
→ 여행 결산
→ 여행 유형 결과
→ 개인/모임 데이터 축적
→ 다음 여행 개인화
```

UI는 여행 중심으로 제공하고 데이터는 개인 또는 모임에 누적한다.

**개인 여행**은 DB 에 모임이 없는 여행이다(`trips.group_id = null` · `owner_type = PERSONAL`). 사용자 화면에서는 `개인`으로 표현하고, 모임 탭에는 표시용 카드 1장이 놓이며 누르면 `/groups/personal` 로 간다. 1인짜리 모임 행을 만들지 않는다.

**모임은 "만드는 것"이 아니라 초대 링크로 사람이 들어오는 순간 생기는 것이다.** 개인 여행에 초대 링크를 보내고 → 상대가 참여 의사를 보내고 → 여행장이 수락하면 → 그 시점에 서버(RPC)가 모임을 만들고 여행을 `PERSONAL → GROUP` 으로 전환한다. 멤버는 이 경로로만 늘어난다.

```text
개인 여행 (group_id null)
→ 초대 링크 발급 (ACTIVE 멤버 누구나)
→ 상대가 참여 의사 보내기
→ 여행장 수락
→ 모임 생성 + PERSONAL → GROUP 전환 (한 RPC 안에서 원자적으로)
```

> **🔁 변경 (v1 → v2)**

## 7. 핵심 정책

### 7.1 여행 생성과 상시 화면

- 생성은 `누구와 → 기본정보 → 예산·자금 설정`의 3단계 1회성 흐름이다.
  - **1단계 누구와** (`/trips/new/owner`): 개인 · 기존 모임 · 신규 모임. 신규 모임은 **모임 이름만** 받는다(동행자 이름 입력 없음). 결산 완료 과거 여행이 1건 이상이면 개인·기존 모임 모두 "지난 여행 데이터 반영" 토글(기본 ON)을 보여준다.
  - **2단계 기본정보** (`/trips/new/basic`): 여행지(13개 해외 목적지 목록에서만 선택 · 지역 세그먼트 필터 + 검색), 일정, 인원(기존 모임 = 멤버 수, 신규 모임 = 2명 기본, 개인 = 1명 고정). **여행 스타일은 이 단계에서 묻지 않는다.**
  - **3단계 예산·자금** (`/trips/new/budget-fund`): 방식 선택 카드 없이 **추천 예산이 기본값으로 먼저 나온다.** 추천 방식일 때만 여행 스타일(budget / standard / comfort 3단계)을 고르고, 근거 상품 체크박스 · 예비비 비율 · 카테고리별 AI↔직접 전환 · 지난 여행 편차 개별 제외로 구성을 고친다. 히어로에서 직접 입력으로 전환할 수 있다. 여행자금은 연결된 계좌(MOCK) / 직접 입력(MANUAL) / 0원(ZERO) **3택**. 고른 근거 상품은 생성 시점에 세부 계획 항목으로 저장된다.
- 생성 후 핵심 상시 화면은 `2-2 여행 준비 홈`이다. 메인 카드는 세로형 **수하물 태그 카드**다.
- 이후 수정은 생성 흐름 재진입이 아니라 **별도 수정 화면 `/trips/[tripId]/edit`** 에서 처리한다. 수정 가능 항목은 **일정·인원**뿐이다. 목적지·모임은 바꿀 수 없다(목적지를 바꾸려면 새 여행). `ENDED` / `SETTLED` 는 수정 차단. 초대 링크 발급·참여 의사 수락도 이 화면에서 한다.
- **수동 "여행 종료" 버튼은 없다.** 출발일이 되면 `TRAVELING`, 종료일 다음 날 `ENDED` 로 앱 진입 시 자동 전환된다(`closeTripIfEnded`). `SETTLED` 는 사용자 확인 없이 자동 확정하지 않는다. 서버 배치가 없어 "앱을 열어야" 전환된다는 한계가 있다.

### 7.2 금융 연결

- 금융계좌 연결은 필수가 아니다.

### 7.3 예산과 거래

- 예산 계획이 서비스의 중심 데이터다. 예산 금액은 `recommended_amount`(불변) · `personalized_amount` · `planned_amount` 3칼럼이며 타입으로 강제된다. 개인화는 `personalized` 까지만 쓰고 `planned` 는 사용자 행동에서만 바뀐다.
- 거래는 예산 카테고리에 매핑되어 실제 사용금액을 갱신한다. MVP 는 1 거래 = 1 카테고리.
- 카테고리 내부 목록은 추천 관광지가 아니라 이번 여행에서 돈을 쓸 세부 계획 항목이다. 추가·수정·삭제에 더해 **AI 계획 후보 제안**(Edge Function `plan-suggestions`)이 있고, 카테고리 화면 안에서 지출을 직접 입력할 수 있다.
- **예산(카테고리 금액) 수정은 `PLANNING` 상태에서만** 가능하다. `TRAVELING` 은 계획 항목만 고칠 수 있다. `SETTLED` 는 전 화면 읽기 전용.
- 목표 예산은 카테고리 합계의 파생값이다. BUDGET-01 에는 금액 수정 UI 가 없고 "이 금액으로 확정하기" + 개인화 토글만 있다. 금액은 BUDGET-02 에서 고치면 합계가 역산된다.
- 가상 여행 금고는 항공 → 숙박 → 보험 → 액티비티 → 교통 → 식비 → 쇼핑 → 예비비 **우선순위로 자동 배분**한다. BUDGET-01 진입 시 `prepared_amount` 를 저장한다.
- 거래 자동 분류는 **LLM**(`classify-transaction`) + 규칙 fallback 이다. 결과는 `AUTO` 로 저장되어 "확인 필요" 필터에 잡히고 사용자가 수정한다. "확인 필요" 사유는 카테고리 없음 · 신뢰도 낮음 · 환불 상태 3종.
- **영수증 스캔**(`receipt-scan`)으로 거래를 입력할 수 있다. 소스 선택 시트 · 스캔 오버레이 · `?scan=receipt` 딥링크.
- 여행자금/입출금은 두 화면이다. FUND-01 = 요약·입출금 시트·최근 10건, 전체 내역은 `/trips/[tripId]/funds/transactions`(FUND-04). 목록 스와이프는 수정·삭제, 카테고리 변경은 탭 → 상세 시트.
- 핵심 거래 입력과 기본 결산은 유료 횟수 제한을 두지 않는다.

### 7.4 여행 유형 결과

- 여행 1회 결산부터 유형을 산출한다.
- 유형은 **9종 확정**이다: `gourmet`(미식) · `lodging_focused`(숙소 중시) · `experience`(체험) · `shopping`(쇼핑) · `frugal`(절약) · `big_spender`(통 큰 여행자) · `spontaneous`(즉흥형) · `planner`(계획파) · `early_saver`(미리미리형) · `balanced`(균형형 · 기본값).
- 산출은 **규칙 기반 v1** 이다. AI 를 쓰지 않는다. 첫 여행 한 건으로도 결과가 나와야 하고 "왜 이 유형인가"를 카테고리별 숫자로 그대로 보여줘야 하기 때문이다.
- `대표 유형 1개 + 복수 특성/보조 유형`을 재미있는 이미지와 함께 보여준다.
- 근거는 목표·실제 총액, 많이 쓴 항목, 초과/절약 항목을 간략히 제공한다. 지출 외에 **준비 행동 2종**(세부 계획 개수 → 즉흥형, 자금 완납 시점 → 미리미리형)도 입력으로 쓴다.
- 결과는 여행 홈에서 자동 생성·1회 저장(`ensureTripTypeResult`)되고 `/trips/[tripId]/type-result` 에서 본다. 종료 홈에는 유형 카드 · 결과 오버레이 · 스토리 시트 · 결산 영수증 · 여행 기록 카드 · 카테고리 결산 그리드가 있다.
- 상세한 분석은 여행 결산으로 분리한다.

> **🔁 변경 (v1 → v2)**
> - **이전(v1)**: "여행 1회 결산부터 유형 산출 / 대표 1개 + 보조 / 근거 간략 / 상세는 결산으로." 유형 개수·산출 방식 미정(README §5 #6 "6개 임시, 확정 전엔 화면 안 만듦").

### 7.5 멤버십 — 초대 · 참여 · 나가기 · 위임 · 취소 · 탈퇴 (신설)

여행 멤버십의 권한 lifecycle 은 DB(RLS · GRANT · SECURITY DEFINER RPC)에서 강제한다. 화면은 이를 안내할 뿐 우회할 수 없다. 상세는 `10_여행초대정책_v2.md` · `11_모임정책_v2.md` · `12_여행초대_승인_RPC계약_v1.md` · `15_회원탈퇴정책_v1.md` · `16_여행멤버십_보안_v1.md` 가 기준이다.

| 단계 | 정책 요약 |

| 초대 링크 발급 | ACTIVE 멤버 누구나 발급(`get_or_create_trip_invite` · 서버 token 생성 · 7일 재사용). 인원이 찼으면 화면에서 초대 버튼 비활성(서버는 링크 유효 유지) |

### 7.6 알림 (신설)

- 알림의 Source of Truth 는 `public.notifications` 다. 생성은 SECURITY DEFINER RPC 안에서 한다(Edge Function 아님). Push 는 전달 채널일 뿐이다.
- 멤버십 이벤트 전부에 producer 가 있다: 초대 도착 · 참여 의사 도착 · 수락 · 거절 · 새 멤버 합류 · 나감 · 여행장 변경 · 취소 요청/동의/확정.
