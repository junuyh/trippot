# 15. 회원탈퇴 정책 v1 (팀 확정 · 2026-09-17)

| 항목 | 내용 |
|---|---|
| 상태 | 확정. 구현: `supabase/migrations/20260917000001_account_withdrawal.sql` · `lib/supabase/queries/users.ts` · `lib/auth/AuthProvider.tsx` · `app/withdrawal-pending.tsx` |
| 배경 | 이전 구현은 `users.deleted_at` 만 찍고 로그아웃 → 같은 카카오 계정으로 다시 로그인하면 즉시 자동 복구됐다. 팀 회의의 "탈퇴 후 보관" 논의를 30일 유예로 확정한다. |

## 1. 상태 흐름

```
ACTIVE ─(탈퇴 신청)→ PENDING_WITHDRAWAL ─(30일 경과 · 서버 cron)→ WITHDRAWN
                          └─(30일 이내 탈퇴 취소)→ ACTIVE
```

| 상태 | DB (`public.users`) | 앱 |
|---|---|---|
| ACTIVE | `withdrawal_requested_at is null and deleted_at is null` | 정상 |
| PENDING_WITHDRAWAL | `withdrawal_requested_at not null and deleted_at is null` · 예정일 = 요청일 + **30일** | 로그인해도 홈 진입 불가. `/withdrawal-pending` 만 — [탈퇴 취소] · [로그아웃] |
| WITHDRAWN | `deleted_at not null` (tombstone) | 세션이 남아 있으면 끊는다. 되살리지 않는다 |

새 enum · status 컬럼은 두지 않는다. 두 시각으로 가른다.

## 2. 규칙

1. **탈퇴 유예 30일.** 신청 즉시 세션을 끊고 로그인 화면으로 보낸다. 데이터는 아무것도 지우지 않는다.
2. **30일 이내 탈퇴 취소 가능.** 같은 카카오 계정으로 로그인 → 탈퇴 진행 중 화면 → [탈퇴 취소] → ACTIVE. 기존 id · 여행 · 모임 · 기록 그대로.
3. **자동 복구 금지.** 로그인 이벤트(SIGNED_IN · INITIAL_SESSION)로 계정을 되살리지 않는다. 되살리는 길은 사용자가 직접 누르는 취소뿐.
4. **여행장은 위임 후 탈퇴.** 다른 ACTIVE 멤버가 있는 진행 중(PLANNING · TRAVELING · ENDED) 여행의 여행장은 신청이 막힌다(`LEADER_MUST_DELEGATE`). 기존 `delegate_trip_leader`(멤버 관리)로 위임한 뒤 다시 신청한다. 자동 위임 없음. 혼자뿐인 여행은 막지 않는다.
5. **공동 여행 기록 유지 · 금액/정산 불변.** trips · budgets · 카테고리 예산 · 납부 · 입출금 · 지출 · 정산 · 결산 · 게시글 · 댓글 · reactions 는 최종 탈퇴 뒤에도 그대로다. 총 모금액 · 달성률 · 부담금 · 정산 결과가 바뀌지 않는다.
6. **hard delete 금지.** `public.users` 행을 지우지 않는다(대부분의 FK 가 `on delete cascade` 라 공동 기록이 사라진다). 행은 tombstone 으로 남는다.
7. **최종 탈퇴(30일 경과) = 현재 권한 제거 + 식별정보 비식별화.** `finalize_withdrawals()` 가 하루 1회(cron `account_withdrawal_finalize` · KST 03:30) 처리:
   - `trip_members` · `group_members` ACTIVE/INVITED → **LEFT** (기존 상태값 · 행 유지)
   - `trip_join_requests` PENDING → **CANCELED** (행 유지)
   - `trips.leader_user_id` = 본인 → null
   - `notifications` 본인 행 삭제 · `profile-images/{userId}/*` 객체 삭제(공개 URL 차단)
   - `users`: name `'탈퇴한 회원'` · english_name · profile_image_url · auth_provider · auth_provider_user_id → null · `deleted_at` 기록
   - `auth.users` 삭제(카카오 identity 포함). 이를 위해 `users_id_fkey`(auth.users cascade)를 뗐다.
8. **최종 탈퇴 후 같은 카카오 계정은 신규 회원.** auth 가 새 id 를 발급하고 앱이 새 `users` 행을 만든다. 과거 공동 기록의 "탈퇴한 멤버"와 자동 연결하지 않는다.
9. **초대 링크는 건드리지 않는다.** 여행 단위 링크라 한 멤버의 탈퇴로 무효화하지 않는다.
10. **공동 기록의 탈퇴자 표시.** 조회 query 가 `users.deleted_at` 으로 걸러 이름을 null 로 내리고 화면이 "탈퇴한 멤버/회원" 으로 그린다. 같은 여행 안 탈퇴자 구분 번호(1, 2…)는 필요가 확인되면 그때 둔다.

## 3. 서버 함수

| 함수 | 권한 | 동작 |
|---|---|---|
| `request_withdrawal()` | authenticated | 본인 신청. 여행장 검사 → `withdrawal_requested_at = now()`. 멱등. 반환 = 예정일 |
| `cancel_withdrawal()` | authenticated | 본인 취소. `withdrawal_requested_at = null`. 이미 WITHDRAWN 이면 `ALREADY_WITHDRAWN` |
| `finalize_withdrawals()` | cron(postgres)만 | 30일 지난 신청을 §2-7 대로 처리. 앱에서 부를 수 없다 |

오류 코드: `AUTH_REQUIRED` · `NOT_FOUND` · `LEADER_MUST_DELEGATE` · `ALREADY_WITHDRAWN` (message 그대로).

## 4. 프로필 이미지 파일 정리 · MY 보안 (2026-09-17 추가)

- `finalize_withdrawals()` 는 Storage 를 건드리지 않는다(SQL 로 `storage.objects` 를 지우면 파일이 남는다). `users.profile_image_url` 만 비운다.
- 실제 파일은 Edge Function **`withdrawal-cleanup`** 이 Storage API 로 지운다 — 30일 지난 신청 계정의 `profile-images/{uid}/*` 를 지운 뒤 `finalize_withdrawals()` 를 부른다(service_role 전용 · 멱등). 배포 완료.
- **외부 설정 필요(사람이 직접)**: Dashboard → Integrations → Cron 에서 하루 1회 `POST /functions/v1/withdrawal-cleanup` (Authorization: Bearer service_role). pg_net 이 없어 DB cron 이 함수를 직접 부를 수 없다. 이 설정 전까지는 DB cron 이 최종 처리만 하고 파일은 다음 함수 실행 때 정리된다.
- MY 범위 보안(`20260917000002_my_security.sql`): `users` 본인 행만 쓰기 · `reactions` 본인 user_id 로만 · `profile-images` 본인 폴더만 · 탈퇴 대기(`is_account_active()` false) 계정은 MY mutation 거부.
- 테스트 계정으로 30일 경과를 재현할 수 없어 `finalize_withdrawals()` 는 SQL 검토 + 권한 확인까지.
