| # | 위치 | v1 | v2 |

## 0. 이 문서를 읽는 법

이 문서는 **서비스 전체 구조를 한눈에 보기 위한 트리**다.

- **화면 ID와 라우트는 `04_화면목록_v3.md` 가 기준이다.** 이 문서의 번호(1-1, 2-2 등)는 구조 이해용 참조 번호이며 코드에 사용하지 않는다.
- 트리의 하위 항목이 반드시 별도 화면인 것은 아니다. 한 화면 안의 섹션인 경우가 많다. 실제 화면 단위는 화면목록을 따른다.
- 화면 흐름과 분기 조건은 `02_유저플로우_v1.md` 가 기준이다.
- 기능 우선순위는 `03_요구사항정의서_v1.md` 가 기준이다.

├─ 현재 여행자금                              FUND-01
│  ├─ 누적 모금액 · 목표 여행비 · 앞으로 필요한 금액
│  └─ 자금 추가 / 차감            [바텀시트]   ← v2 추가
├─ 자금 관리 방식 (계좌 연결 / 직접 입력)
├─ 입출금 전체 내역                           FUND-01

**정책:** 직접입력 금액과 연결계좌 잔액을 합산하지 않는다. 확인 후 계좌 잔액으로 대체한다.

#### 2-4-1. 금액 용어 — 혼용하지 않는다

| 용어 | 뜻 | 결제하면 |
|---|---|---|
| **누적 모금액** | 지금까지 확보한 총 여행자금 | **줄지 않는다** |
| **현재 잔액** | 계좌·모임통장에 지금 남은 금액 | 줄어든다 |
| 목표 여행비 | 카테고리별 설정 예산 합계 | — |
| 실제 사용 | 결제가 확정된 여행 지출 | — |

TRIP-HOME 보딩패스의 비행기 위치와 BUDGET-01 준비율은 **누적 모금액** 기준이다.
항공권을 샀다고 여행 준비 진행률이 뒤로 가면 안 된다.

단, 모금 취소·입금 취소·환불처럼 **누적 모금 자체가 취소된 경우**에는 다시 계산한다.

> ⚠️ 현재 `fund_sources.current_amount` 는 등록·동기화 시점에만 쓰는 값이라
> 거래가 쌓여도 변하지 않는다. **그래서 지금은 이 값이 곧 누적 모금액이다.**
> FUND-02(계좌 재동기화)를 붙이면 이 전제가 깨진다. 그때 누적 모금액을 따로
> 보관할지 입금 합계로 계산할지 정해야 한다. `[검토 필요]`

#### 2-4-2. '확인 필요' 필터 — 지금 판정할 수 있는 것만

| 사유 | 판정 근거 | 지금 가능? |
|---|---|---|
| 카테고리 없음 | `transactions.budget_category_id is null` | ✅ |
| 자동 분류 신뢰도 낮음 | `transactions.category_confidence` (0–100) | ✅ |
| 계획 연결 후보가 여러 개 | 후보 계산 로직 없음 | ❌ |
| 중복 가능성 (카드 승인 ↔ 계좌 출금) | 승인/출금 구분 칼럼 없음 | ❌ |
| 환불·취소 확인 | 환불 플래그 없음 | ❌ |

**❌ 세 가지는 FUND-02(계좌 연결) 이후다.** 스키마가 없다.
지금 필터는 위 두 가지로만 만든다.

같은 이유로 **'환불 예정 금액'·'미확정 카드 거래'를 결산 화면에 표시하지 않는다.**

#### 2-4-3. 자동 탐지처럼 말하지 않는다

FUND-02 가 없으면 앱에 입력된 거래만 안다. 계좌를 훑어 누락을 찾아낸 게 아니다.

| 상태 | 문구 |
|---|---|
| 직접 입력만 | `기록된 지출 내역 확인하기` |
| 계좌 연결 이후 | `확인할 거래 N건 보기` |

MVP 금융 데이터는 전부 Supabase Mock 이다. (`CLAUDE.md` 11장)

│  ├─ 목표 여행비 / 실제 여행비
│  ├─ 가장 많이 지출한 카테고리
│  ├─ 예상보다 많이 쓴 카테고리
│  ├─ 예상보다 절약한 카테고리
│  └─ 카테고리별 대표 수치
├─ 데이터 기준 안내
├─ [결과 이미지 저장]
├─ [친구에게 공유]

### 2-6. 여행 결산

> 화면: `SETTLE-01` · `/trips/[tripId]/settlement` · MVP

```
2-6. 여행 결산
├─ 목표 여행비 vs 실제 여행비
├─ 초과 / 절약 금액과 비율
├─ 카테고리별 예상 vs 실제
├─ 전체 여행비 내역
├─ 확인할 거래 N건        → FUND-01 '확인 필요' 필터      ← v2 추가
├─ 지출 미연결 계획 N건   → 해당 카테고리 BUDGET-02        ← v2 추가
├─ 개인 / 모임 소비 데이터 반영
└─ 다음 여행 예산에 활용
```

여행 기간 종료 시 자동으로 결산을 유도한다. 사용자 확인 후 진행한다.
결산 확정 시점의 값을 스냅샷으로 보존한다.

#### 2-6-1. 결산 중 이동 흐름

```
TRIP-HOME-02 (ENDED)
  ↓ 여행비 결산 보기
SETTLE-01
  ├─ 확인할 거래 ──────→ FUND-01 (확인 필요 필터) → FUND-03 거래 상세
  └─ 지출 미연결 계획 ──→ 해당 카테고리 BUDGET-02
```

**미분류 거래를 임의의 BUDGET-02 로 보내지 않는다.**
카테고리가 없는 거래는 '어느 카테고리 화면인가' 에 답할 수 없다.
BUDGET-02 는 카테고리가 정해진 뒤 계획과 실제를 비교하는 자리다.

반대로 **지출 미연결 계획은 이미 카테고리가 정해져 있다.** 그래서 BUDGET-02 로 보낸다.

```
스카이라이너 왕복권 — 실제 지출이 연결되지 않았어요
  → 결제하지 않았어요 / 지출 직접 입력 / 기존 거래 연결
```

#### 2-6-2. 결산 상태 — 새 상태값을 만들지 않는다

`trips.status` 는 이미 다섯 값으로 고정돼 있다.

```sql
check (status in ('PLANNING', 'TRAVELING', 'ENDED', 'SETTLED', 'DELETED'))
```

| 상태 | 뜻 |
|---|---|
| `ENDED` | **결산 중.** 여행 일자는 끝났고 거래 검토가 남았다 |
| `SETTLED` | **결산 완료.** `settlements.confirmed_at` 이 채워졌다 |

> ⚠️ `SETTLEMENT_IN_PROGRESS` 같은 새 상태를 만들지 않는다.
> `ENDED` 가 이미 그 뜻이다. 새로 넣으려면 CHECK 제약 마이그레이션과
> 공유 상수 `TRIP_STATUS` 변경이 필요해 모든 화면이 영향을 받는데, 얻는 게 없다.

#### 2-6-3. 상태별 수정 권한

**화면을 새로 만들지 않는다.** 같은 화면에서 데이터와 권한만 바꾼다.

| | `PLANNING` / `TRAVELING` | `ENDED` (결산 중) | `SETTLED` (결산 완료) |
|---|---|---|---|
| 설정 예산 수정 | ✅ | ❌ | ❌ |
| 계획 추가·삭제·체크 | ✅ | ❌ | ❌ |
| 과거 예산 추천 적용 | ✅ | ❌ | ❌ |
| 실제 지출 추가 | ✅ | ✅ | ❌ |
| 거래 분류 확인 | ✅ | ✅ | ❌ |
| 계획–거래 연결·해제 | ✅ | ✅ | ❌ |

결산 완료 후 거래를 고쳐야 하면 **결산을 다시 열어 `ENDED` 로 되돌린다.** `[검토 필요]`

여행 유형은 **결산 완료 이후에만** 확정·공개한다.
결산 중에는 `지출 확인을 마치면 여행 유형이 공개돼요` 로 안내한다.
