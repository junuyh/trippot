| # | 변경 | 내용 | 이유 |

## 0. 목적

배포 전에 **어떤 순간에 / 어떤 이름으로 / 무엇을 담아** 기록할지 확정한다.

Analytics는 소급이 불가능하다. 심지 않고 배포한 기간의 데이터는 영구히 존재하지 않는다.
이 문서가 `lib/analytics/events.ts` 의 유일한 원본이다.

## 1. 설계 원칙

**① 모든 클릭을 기록하지 않는다**
아래 다섯 가지 목적에 쓰이는 이벤트만 정의한다.

```
North Star / 핵심 Funnel / AARRR / 가설 검증 / BM 전환
```

**② 분기점을 기록한다**
User Flow의 마름모(조건)가 이벤트 발생 지점이고, 분기에서 나가는 화살표 라벨이 파라미터 값이다.
"무엇을 눌렀나"보다 **"무엇을 선택했나"** 를 남긴다.

**③ 상태값은 Analytics로 재지 않는다**
금액, 달성률, 예상 vs 실제 차이는 DB에서 쿼리한다. (3장 참조)

**④ 이벤트는 사후 추가가 비싸다**
이름은 지금 고정한다. 이름 변경은 나중에 일괄 치환이라 싸고, 안 심은 로그를 심는 건
모든 화면을 되돌아가야 해서 비싸다. **고도화 단계 이벤트도 이름은 v1에서 확정한다.**

## 2. 전송 대상 — 3중 기록

`track()` 하나에서 세 곳으로 보낸다.

| 대상 | 역할 |
|---|---|
| **Amplitude** | 퍼널·리텐션 차트. 발표 자료에 넣을 시각화 |
| **Firebase Analytics** | GA4 앱 버전. 부트캠프 ⑩ "GA 기준" 요건 충족 |
| **event_log (Supabase)** | SQL 조인. ⑭ 분석 리포트의 실제 근거 |

```ts
export function track(name, params) {
  if (__DEV__) return console.log('[track]', name, params);
  amplitude.track(name, withCommonParams(params));
  analytics().logEvent(name, withCommonParams(params));
  supabase.from('event_log').insert(...).then(null, () => {});  // 실패해도 앱은 계속
}
```

**Firebase 설정 주의:** `google-services.json` + Expo config plugin 설정이 필요하다.
EAS 빌드 파이프라인을 처음 뚫을 때 함께 넣는다. 나중에 추가하면 빌드를 다시 돌려야 한다.

## 3. Analytics vs DB — 무엇을 어디서 재는가

판별 기준 두 개.

```
분모가 사람인가, 여행인가?          사람 → Analytics / 여행 → DB
나중에 다시 계산할 수 있나?          가능 → DB / 지나간 순간 → Analytics
```

### Analytics

행동, 퍼널, 이탈. **DB에 흔적이 남지 않는 것.**

- 화면 진입과 이탈 지점
- 여행 생성 퍼널 단계별 통과
- 분기 선택값 (개인·모임 / 추천·직접입력 / 계좌·수기·0원)
- 예산 수정·항목 추가가 **일어났다는 사실**
- 거래 카테고리 수정 발생
- 팁·보험 CTA 노출과 클릭
- 결산 도달과 확정
- 개인화 반영·제외 선택

### DB (Supabase 쿼리)

상태와 결과. **언제든 다시 계산 가능한 것.**

- 목표 여행비 금액 분포
- 현재 여행자금 / 목표 대비 달성률
- `recommended_amount` → `planned_amount` 차이
- 카테고리별 예상 vs 실제
- 여행당 세부 계획 항목 수
- 자동분류 정확도 (auto 매핑 중 사용자가 바꾼 비율)
- 모임당 여행 수

### 두 개를 잇는 장치

**모든 이벤트에 `trip_id` 를 붙인다.**
Analytics에서 이탈한 `trip_id` 목록을 뽑아 DB에서 조회하면 두 데이터를 이어 볼 수 있다.
없으면 "어디서 이탈했나"와 "예산이 얼마였나"가 영원히 따로 논다.

## 5. 공통 파라미터

`track()` 이 모든 이벤트에 자동으로 붙인다. 개별 호출에서 넘기지 않는다.

| 파라미터 | 타입 | 설명 |
|---|---|---|
| `anon_id` | string | 최초 실행 시 발급, AsyncStorage 저장 |
| `user_id` | string \| null | 로그인 후 |
| `trip_id` | string \| null | 여행 컨텍스트가 있으면 |
| `platform` | `ios` \| `android` | |
| `app_version` | string | |
| `env` | `development` \| `production` | |

**로그인 전 처리:** 홈 진입·여행 만들기 클릭은 로그인 전에 발생한다.
`anon_id` 로 먼저 기록하고, 로그인 시점에 `user_id` 매핑을 한 번 남긴다.
하지 않으면 유입 대비 전환율의 **분모가 틀어진다.**

**개발 환경:** `__DEV__` 에서는 전송하지 않는다. 실사용자 n이 20~50명 규모라
개발 클릭이 섞이면 데이터가 망가진다.

**`trip_status` 값**

`trip_home` 화면에서만 채운다. **그 외 화면에서는 `null`** 이다.
값은 `lib/constants/status.ts` 의 `TRIP_STATUS` 를 쓴다. 리터럴 금지.

```
PLANNING   TRAVELING   ENDED   SETTLED   DELETED
```

> **왜 필요한가**
> `TRIP-HOME-01`(여행 준비 홈)과 `TRIP-HOME-02`(종료 상태 여행 홈)는
> `/trips/:tripId` 라는 **같은 라우트를 `trip.status` 로 분기**한다. (`04_화면목록_v3.md` §5)
> `screen_name` 만으로는 둘이 구별되지 않아, "종료된 여행 홈에 몇 명이 들어와서
> 몇 명이 결산을 확정했는가"를 잴 수 없다. 결산 도달률의 분모가 사라진다.

**아직 `screen_name` 값이 없는 화면 (고도화 7개)**

| 화면 ID | 화면명 | 단계 |

이 화면들은 `useScreenView` 를 호출하지 않는다. 코드에 TODO 주석만 있다.
**임의로 값을 만들지 않는다.** 해당 화면 구현 시점에 이 문서를 갱신한 뒤 추가한다. (11장)

### 7-8. 여행 팁 커뮤니티 (BM 2)

팁은 구매 / 평가 / 찜 / 댓글을 갖춘 커뮤니티다. 범위가 커서 단계를 나눈다.

## 8. 핵심 퍼널

```
① screen_viewed (home)
② trip_create_started
③ trip_companion_selected
④ trip_basic_info_submitted
⑤ budget_method_selected
⑥ budget_target_confirmed      ← Proxy NSM
⑦ travel_fund_registered
⑧ trip_created                 ← Activation
─────────── 이후 ───────────
⑨ budget_plan_saved
⑩ transaction_categorized
⑪ settlement_confirmed
⑫ trip_created (user_trip_count >= 2)   ← 재사용
```

**6주 안에 실사용 데이터가 나오는 구간은 ①~⑨까지다.**
⑩ 이후는 여행을 실제로 다녀와야 하므로 n이 거의 0이다. UT로 대체한다.
발표에서 이 경계를 명시하는 것이 억지로 숫자를 만드는 것보다 낫다.

## 9. 가설 ↔ 이벤트 매핑

| 가설 | 이벤트 | 보조 |
|---|---|---|
| 1. 추천이 예산 설정 시간을 줄인다 | `budget_method_selected` → `budget_target_confirmed` 경과 시간 | DB: 추천액 대비 수정 폭 |
| 2. 총무가 모금 관리에 부담을 느낀다 | — | UT / 인터뷰 |
| 3. 가상 금고가 준비 상태 이해를 돕는다 | `screen_viewed(trip_home)` 재방문 빈도 | UT |
| 4. 개인화 예산이 더 현실적이다 | `personalization_applied` | DB: 반영/미반영 예산 정확도 비교 |
| 5. 과거 데이터 재사용을 위해 재방문한다 | `trip_created(user_trip_count>=2)`, `past_data_apply_selected` | |
| 6. 소액이면 팁을 산다 | `tip_impression` → (고도화) `tip_purchase_intent` | **MVP는 UT로 검증** |
| 7. 수익이 되면 팁을 쓴다 | — | UT |

**가설 2·3·7은 정량 검증이 불가능하다.** ⑬ UT 설계에서 다룬다.

```
- 뒤로가기, 스크롤, 탭 전환
- 입력 필드 포커스
- 모달 열기/닫기 (전환에 직결되는 것 제외)
- 설정 화면 내부 동작
- 목록 아이템 단순 조회
- 이미 DB에 남는 상태값 (잔액, 달성률 등)
```

## 11. 구현 규칙

```ts
import { track } from '@/lib/analytics/track';
import { EVENTS } from '@/lib/analytics/events';

track(EVENTS.BUDGET_METHOD_SELECTED, { method: 'recommended' });
```

- 이벤트 이름은 `events.ts` 상수만 사용한다. 문자열 리터럴 금지.
- **이 문서에 없는 이벤트를 임의로 추가하지 않는다.** 필요하면 사람에게 요청한다.
- 화면 진입은 `useScreenView(SCREENS.XXX)` 로만 기록한다.
- **성공한 결과에만 쏜다.** 저장 버튼을 눌렀지만 실패했으면 쏘지 않는다.
- 화면 이동 전에 쏜다. 이동 후 쏘면 유실될 수 있다.
- 고도화 이벤트는 `events.ts` 에 상수만 정의하고 호출하지 않는다.

   → tip_impression 이 빈 화면이 되지 않게 하려면 필요
