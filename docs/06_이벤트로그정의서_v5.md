## 1. 설계 원칙

**① 모든 클릭을 기록하지 않는다**
아래 다섯 가지 목적에 쓰이는 이벤트만 정의한다.

```
North Star / 핵심 Funnel / AARRR / 가설 검증 / BM 전환
```

**② 분기점을 기록한다**
User Flow의 마름모(조건)가 이벤트 발생 지점이고, 분기에서 나가는 화살표 라벨이 파라미터 값이다.
"무엇을 눌렀나"보다 **"무엇을 선택했나"** 를 남긴다.

**③ 상태값은 Analytics로 재지 않는다**
금액, 달성률, 예상 vs 실제 차이는 DB에서 쿼리한다. (3장 참조)

**④ 이벤트는 사후 추가가 비싸다**
이름은 지금 고정한다. 이름 변경은 나중에 일괄 치환이라 싸고, 안 심은 로그를 심는 건
모든 화면을 되돌아가야 해서 비싸다. **고도화 단계 이벤트도 이름은 v1에서 확정한다.**

> **v5 덧붙임 — ⑤ 정의한 이벤트는 호출되는지 주기적으로 대조한다.**
> ④ 대로 이름을 먼저 확정해 둔 결과 **정의 67개 중 40개가 호출부 없이 남아 있다** (§7 구현 상태 열).
> 정의만 있는 이벤트는 노이즈는 아니지만, "심어져 있다" 고 믿게 만들어 퍼널 문서(13 v1 §3-3 · §3-5)에
> 실제로는 없는 단계가 들어갔다. 문서 갱신 때마다 `grep -rn "track(EVENTS\."` 결과를 §7 에 반영한다.

## 3. Analytics vs DB — 무엇을 어디서 재는가

판별 기준 두 개.

```
분모가 사람인가, 여행인가?          사람 → Analytics / 여행 → DB
나중에 다시 계산할 수 있나?          가능 → DB / 지나간 순간 → Analytics
```

### Analytics

행동, 퍼널, 이탈. **DB에 흔적이 남지 않는 것.**

- 화면 진입과 이탈 지점
- 여행 생성 퍼널 단계별 통과
- 분기 선택값 (개인·모임 / 추천·직접입력 / 계좌·수기·0원)
- 예산 수정·항목 추가가 **일어났다는 사실**
- 거래 카테고리 수정 발생
- 팁·보험 CTA 노출과 클릭
- 결산 도달과 확정
- 개인화 반영·제외 선택

### DB (Supabase 쿼리)

상태와 결과. **언제든 다시 계산 가능한 것.**

- 목표 여행비 금액 분포
- 현재 여행자금 / 목표 대비 달성률
- `recommended_amount` → `planned_amount` 차이
- 카테고리별 예상 vs 실제
- 여행당 세부 계획 항목 수
- 자동분류 정확도 (auto 매핑 중 사용자가 바꾼 비율)
- 모임당 여행 수

### 두 개를 잇는 장치

**모든 이벤트에 `trip_id` 를 붙인다.**
Analytics에서 이탈한 `trip_id` 목록을 뽑아 DB에서 조회하면 두 데이터를 이어 볼 수 있다.
없으면 "어디서 이탈했나"와 "예산이 얼마였나"가 영원히 따로 논다.

> **v5 덧붙임.** 사람 단위로 잇는 장치는 `user_id` 인데, 이 값이 현재 모든 이벤트에서 null 이다 (§5).
> `event_log.user_id` 가 비어 있으면 "여행을 만든 사람 중 몇 명이 결산까지 갔나" 를 `anon_id` 로만 이어야 하고,
> 기기를 바꾸거나 앱을 지운 사용자는 끊긴다.

## 5. 공통 파라미터

`track()` 이 모든 이벤트에 자동으로 붙인다. 개별 호출에서 넘기지 않는다.

| 파라미터 | 타입 | 설명 | 현재 실제 값 (v5 대조) |
|---|---|---|---|
| `anon_id` | string | 최초 실행 시 발급, AsyncStorage 저장 | 정상. `app/_layout.tsx:147` 의 `initAnalytics()` 가 앱 시작 시 발급 |
| `user_id` | string \| null | 로그인 후 | **항상 null.** `setAnalyticsUser()` 호출부 없음 (아래) |
| `trip_id` | string \| null | 여행 화면이 `setTripContext(tripId)` 로 설정한 값. **설정하지 않으면 null 이다** | `/trips/:tripId` 아래 12개 화면이 `useTripContext(tripId)` 로 설정 (2026-09-07 7556cea 이후). 생성 흐름(`/trips/new/*`)은 여행이 아직 없어 null 이 맞다 |

**로그인 전 처리:** 홈 진입·여행 만들기 클릭은 로그인 전에 발생한다.
`anon_id` 로 먼저 기록하고, 로그인 시점에 `user_id` 매핑을 한 번 남긴다.
하지 않으면 유입 대비 전환율의 **분모가 틀어진다.**

> **🔁 변경 (v4 → v5) — `user_id` 가 저절로 붙지 않는다**
> - **이전(v4)**: "`user_id` — 로그인 후" 라고만 적혀 있었다. `trip_id` 는 v4 에서 같은 문제를 찾아 §5 에 규칙을 넣었다.
> - **문제정의**: `lib/analytics/track.ts:129` 의 `setAnalyticsUser(userId)` 를 **앱 어디에서도 부르지 않는다** (`grep -rn setAnalyticsUser app components lib` → 정의 1곳뿐). 따라서 (a) `event_log.user_id` 가 전부 null, (b) Amplitude `setUserId` 가 한 번도 실행되지 않아 사용자 단위 리텐션·퍼널이 `anon_id` 에만 의존한다. `login_completed` 가 정의만 있는 것(§7-0)과 같은 뿌리다 — 로그인 성공 지점(`lib/auth/AuthProvider.tsx:142`, `SIGNED_IN | INITIAL_SESSION`)에 Analytics 연결이 하나도 없다.
> - **의사결정**: 규칙 — **`AuthProvider` 가 세션을 얻거나 잃을 때 `setAnalyticsUser(user.id | null)` 을 부른다.** 화면이 아니라 세션 관리 한 곳에서만 부른다(`trip_id` 의 `useTripContext` 와 같은 방식). `login_completed` 도 같은 자리에서 쏜다 (§7-0). 2026-09-18 · 근거 `lib/analytics/track.ts:125-140` · `lib/auth/AuthProvider.tsx:118-146` · 13 v1 §5 제안 1
> - **상태**: **[검토 필요]** — `AuthProvider.tsx` 는 인증 담당 소유. 코드 수정은 담당자 확인 후. 이 문서는 규칙만 정한다

**개발 환경:** `__DEV__` 에서는 전송하지 않는다. 실사용자 n이 20~50명 규모라
개발 클릭이 섞이면 데이터가 망가진다.

**⚠️ `trip_id` 는 저절로 붙지 않는다 (v4 보강 · v5 에서 해소 확인)**

`track()` 이 자동으로 채우는 것은 맞지만, 그 값은 `setTripContext(tripId)` 로
누군가 미리 설정해 둔 것이다. v3 까지 이 함수를 호출하는 화면이 하나도 없어
모든 이벤트의 `trip_id` 가 null 이었다.

**규칙 —** `/trips/:tripId` 아래 모든 화면은 진입 시 컨텍스트를 설정하고
벗어날 때 해제한다. 화면마다 손으로 `track()` 에 넘기지 않는다.
기준 파일 `lib/hooks/useTripContext.ts`.

> **🔁 변경 (v4 → v5)**
> - **이전(v4)**: 규칙만 있고 호출 화면이 없었다.
> - **문제정의**: 해소 여부를 문서가 확인하지 않았다.
> - **의사결정**: 2026-09-07 (7556cea) 부터 아래 12개 화면이 `useTripContext(tripId)` 를 부른다 — `index` · `edit` · `budget/index` · `budget/[categoryId]` · `funds/index` · `funds/connect` · `funds/transactions/index` · `funds/transactions/[transactionId]` · `settlement` · `type-result` · `insurance` · `contributions`. `insurance_cta_clicked` 등 일부 호출부가 `trip_id` 를 명시로 넘기는 것은 이중 안전장치로 유지한다. 근거 `grep -rn useTripContext app`

**`past_data_apply_selected` 기록 시점과 `interacted`** (v3)

토글이 **기본 ON** 이라 만지지 않고 지나가는 사용자가 생긴다. 선택 시점에만 기록하면
그 사람들이 통째로 빠져 **분모가 '토글을 만진 사람' 으로 좁아진다.**
그래서 선택이 아니라 **TRIP-01 '다음' 을 누르는 시점에 최종값으로 1회** 기록한다.
앞뒤로 오가며 다시 눌러도 값이 그대로면 재발생하지 않는다. 값을 바꿔서 오면 그때 다시 쏜다.
분석은 흐름당 마지막 이벤트를 본다.

| `applied` | `interacted` | 뜻 |
|---|---|---|
| `true` | `false` | 기본 ON 을 그대로 두고 통과 (관성) |
| `true` | `true` | 껐다가 다시 켬 |
| `false` | `true` | 직접 끔 |

`applied=false, interacted=false` 는 발생하지 않는다. 기본값이 ON 이기 때문이다.
**`interacted` 없이 `applied` 만 보면 관성과 능동적 수용이 섞여 반영 비율이 부풀려진다.**
개인 여행에도 똑같이 묻는다(README #16) — 결산 완료 과거 여행이 0건이면 토글이 뜨지 않고 이벤트도 없다.

**`budget_product_changed.category`** (v3)

§7-2 의 **category 값 규약과 동일**하다 (`flight` `accommodation` `food` `transport`
`activity` `shopping` `insurance` `reserve`). DB 의 `category_code`(`AIRFARE` 등)를 그대로
쓰지 않는다. `lib/constants/status.ts` 의 `CATEGORY_CODE_TO_ANALYTICS` 를 반드시 거친다.
예비비(`reserve`)에는 근거 상품이 없으므로 이 이벤트가 발생하지 않는다.

**`travel_style_changed`** (v3)

같은 값을 다시 눌러도 발생하지 않는다. 세그먼트는 이미 선택된 것을 또 누를 수 있어서,

`from_style` · `to_style` 값은 §5-1 의 `TRAVEL_STYLE` 3종을 따른다.

**`budget_target_confirmed.edited_category_count`** (v5 확인)

TRIP-03 에서는 `categories.filter(c => c.plannedAmount !== c.recommendedAmount).length` —
**저장 시점에 추천값과 다른 카테고리 수**다 (`N/budget-fund.tsx:997-1000`). 근거 상품을 끄거나 예비비 비율을

**`travel_fund_registered.fund_type` 분포 해석 주의** (2026-09-03 이후)

기존 모임에 연결 계좌가 있으면 TRIP-03 이 **자동으로 그 계좌를 고른다** (`N/budget-fund.tsx:1003-1012` 주석 · 18 §2-17).

> "예산 화면 도달자 중 N%가 보험 CTA를 눌렀다" 가 이번 프로젝트에서 제시 가능한
> 유일한 수익화 숫자다.

**발생 시점 — 화면 진입이 아니라 제휴사로 넘어갈 때다 (v4 명확화)**

INSURANCE-01 진입은 `screen_viewed(insurance)` 가 잡는다.
이 이벤트를 진입에서 쏘면 **"궁금해서 눌러본 사람" 과 "실제로 견적을 본 사람" 이
한 통에 섞여** 두 숫자를 모두 잃는다. 둘을 나눠야 전환율이 나온다.

```
screen_viewed(insurance)   보험 화면에 들어온 사람      ← 분모
insurance_cta_clicked      제휴사로 넘어간 사람         ← 분자
```

**`placement` 값** — 두 개뿐이다. 코드 상수와 1:1이다.

| 값 | 자리 |
|---|---|
| `trip_home` | 여행 홈 하단 '우리 여행 보험료, 1분이면 계산 끝' 배너 |
| `budget_detail` | 여행자보험 카테고리 상세의 '보험료 얼마인지 확인해 볼까요?' + **세부 계획 추가 직후 프로모 모달**(`T/budget/[categoryId].tsx:1624-1635` · 모달 자체는 로그 없음, INSURANCE-01 로 넘어간 뒤 잡는다) |

새 진입점을 만들면 **값을 임의로 늘리지 말고 이 문서부터 고친다.** (11장)

**v5 확인 — `placement = budget_detail` 의 분모가 없다.** BUDGET-02 가 `screen_viewed(budget_category_detail)` 을 쏘지 않는다(§7-0).
"보험 카테고리 상세를 본 사람 중 몇 명이 보험 화면으로 갔나" 는 §7-0 의 `useScreenView` 복구 전까지 못 낸다.
`screen_viewed(insurance)` → `insurance_cta_clicked` 의 견적 확인률만 지금 계산 가능하다.

**`trip_id`** — 이 이벤트는 화면이 명시로 넘긴다. 5장의 `setTripContext` 규칙과
중복이지만, BM 1 은 여행 단위 분해가 핵심이라 컨텍스트 설정이 빠져도 값이 남도록 이중으로 둔다.
(`insurance.tsx:208-214` 주석은 "setTripContext 가 어디에서도 불리지 않는다" 고 적혀 있는데, 같은 화면이 `useTripContext` 를 이미 부른다 — 주석이 낡았다. 동작에는 영향 없다.)

**⚠️ 제휴사는 현재 전부 가상이다.** 실제 제휴가 없어 이동할 곳도 없고,
이 이벤트가 세는 것은 **가입 의사가 아니라 견적 확인 의사**다.
발표·보고에서 "전환율" 이라고 부르지 않는다. **"견적 확인률"** 이다.

### 8-8. 자동 상태 전환이 퍼널 해석에 미치는 영향 (v5 신설 · 18 §3-6)

`PLANNING → TRAVELING → ENDED` 는 **사용자 행동이 아니다.** 출발일이 되면 `TRAVELING`, 종료일 다음날이면 `ENDED` 로,
사용자가 앱을 열어 여행 홈에 들어올 때 `closeTripIfEnded` 가 올린다(`lib/supabase/queries/trips.ts:432-468`). 서버 배치가 없다.
그래서 세 가지를 조심한다. ① 상태 전환 자체는 어느 이벤트에도 남지 않는다 — "여행이 끝난 사람" 의 분모는 Analytics 가 아니라
DB `trips.end_date < today` 로 센다(3장 원칙과 일치). ② `screen_viewed(trip_home, ENDED)` 와 `settlement_prompted(auto)` 는
"종료 후 앱을 다시 연 사람" 이지 "종료된 사람" 이 아니다. 결산 도달률의 분모를 이 둘로 잡으면 앱을 안 연 사람이 빠져 **도달률이 과대**된다.
③ 종료 후 한 번도 앱을 열지 않은 여행은 DB 상태가 `PLANNING` 인 채로 남는다 — 상태값으로 "여행 중/종료" 를 세면 그 여행들이 빠진다.
`SETTLED` 만 사용자 행동(`settlement_confirmed`)이고, `CANCEL_PENDING`/`CANCELED` 는 §7-9 이벤트가 심어지기 전까지 DB 로만 본다.

### 8-9. 13 v1 의 집계와 다른 점

13 v1 §2 는 "정의 85 · 호출 35 · `screen_viewed` 18곳/16종" 이라 적었다. 같은 커밋(464db77 · PR #108)에서
`grep` 으로 다시 세면 **정의 67(EVENTS) + 18(SCREENS) · 호출 27종(호출부 41곳) · `screen_viewed` 17곳/14종** 이다.
현재(eeeb2eb)는 호출부 40곳 · `screen_viewed` 16곳/14종으로, `events.ts` 는 그 사이 바뀌지 않았다.
어느 방법으로 셌는지 13 v1 에 남아 있지 않아 원인을 단정하지 않는다. **13 v2 갱신 시 이 문서 §7 의 표를 기준으로 맞춘다** [검토 필요].

- **이 문서에 없는 이벤트를 임의로 추가하지 않는다.** 필요하면 사람에게 요청한다.
- 화면 진입은 `useScreenView(SCREENS.XXX)` 로만 기록한다. **한 `SCREENS` 값을 두 화면이 나눠 쓰지 않는다.** (v5 · FUND-01/04)
- **성공한 결과에만 쏜다.** 저장 버튼을 눌렀지만 실패했으면 쏘지 않는다.
- 화면 이동 전에 쏜다. 이동 후 쏘면 유실될 수 있다.
- 고도화 이벤트는 `events.ts` 에 상수만 정의하고 호출하지 않는다.
- (v5) 화면 구현 시 뼈대의 `useScreenView` 를 **지우지 않는다.** 지워야 하면 로그 변경으로 보고 담당에게 알린다 (CLAUDE.md 13장). 2026-08-28 에 세 화면에서 조용히 사라진 것이 §7-0 의 문제다.
- (v5) `/trips/:tripId` 아래 새 화면은 `useTripContext(tripId)` 를 먼저 부른다.

## 12. seed.sql 요구사항

이 문서의 이벤트가 UT에서 실제로 발생하려면 아래 데이터가 필요하다.

```
A모임 (민지·서연·다빈·지수)
└─ 완료된 도쿄 여행 1건 (결산 확정, 식비 +22% / 교통 -11%)
   → personalization_offered 가 발생하는 유일한 조건

개인
└─ 완료된 여행 1건

진행 중 여행 1건 (예산 미확정 상태)

도쿄 팁 10~15건   [담당자 미정]
   → tip_impression 이 빈 화면이 되지 않게 하려면 필요
      (v5: tip_impression 노출 UI 가 없으므로 지금은 tip_list 화면용이다)
```

(v5) 종료일이 지난 `PLANNING` 여행 1건이 있으면 `settlement_prompted(auto)` 와 §8-8 의 자동 전환을 UT 에서 재현할 수 있다. seed 는 DB 담당 소유이므로 요청만 남긴다.
