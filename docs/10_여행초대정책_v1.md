## 1. 초대의 대상은 모임이 아니라 여행이다

**사용자 기능으로서 "모임 멤버 초대" 는 없다.** (2026-09-10 확정)

- 모임 상세에 멤버 초대 CTA 를 만들지 않는다
- 모임 초대 링크를 만들지 않는다
- 모임 가입 receiver 화면을 만들지 않는다

초대는 **여행 멤버 초대** 하나뿐이다.

```
여행준비홈 → 설정 → 여행 정보 수정 → 여행 멤버 초대하기
```

모임 멤버십은 여행 참여의 **결과로** 정리되는 것이지, 사용자가 직접 초대해서 만드는 것이 아니다.

---

## 2. 초대 링크를 만들고 공유할 수 있는 사람

**현재 그 여행에 참여 중인 ACTIVE 여행 멤버 누구나** 할 수 있다.

**여행장만 할 수 있는 것이 아니다.**

링크를 뿌리는 일은 되돌릴 수 있다. 실제로 사람이 들어오는 관문은 **수락**이고, 그 수락만 여행장이 쥔다.
(여행 취소가 "요청은 누구나 → 확정은 만장일치" 인 것과 같은 모양이다)

---

## 3. 링크를 받았다고 멤버가 되지 않는다

```
초대 링크  →  참가 신청  →  여행장 승인  →  여행 참여 확정
```

초대는 **"참가 신청의 진입점"** 이지 "즉시 가입" 이 아니다.

이 사실은 **초대 메시지 문구에도 드러나야 한다.** "링크를 눌러 들어와 주세요" 처럼
승인 절차 없이 참여가 끝나는 것처럼 읽히는 표현을 쓰지 않는다.

수락 전에는 예산·금액·멤버 목록을 볼 수 없다. (POL-INV-021)

## 4. POL-INV-014 — 여행 초대 링크 재사용 및 만료 후 갱신 **[확정]**

> ⚠️ 이 절이 이 문서를 만든 이유다. 마이그레이션의 한 줄 주석
> "재발급 시 이전 링크를 즉시 무효화한다 (POL-INV-014)" 만 보면 **다르게 해석될 수 있다.** (§8-1)

### 4-1. 확정 정책

1. 여행 초대 링크는 **발급 시점부터 7일간** 유효하다.
2. 동일 링크는 유효기간 동안 **여러 사용자가 사용할 수 있는 다인용 링크**다.
3. 하나의 여행에 **아직 유효한 초대 링크가 있으면 새 링크를 만들지 않는다.**
4. 유효기간 내에 누군가 다시 '여행 멤버 초대하기' 를 실행하면 **현재 유효한 기존 링크를 그대로 재사용한다.**
5. 링크를 처음 만든 멤버가 아닌 **다른 ACTIVE 여행 멤버가 실행해도 똑같이 기존 링크를 재사용한다.**
6. `now() < expires_at` 이면 계속 유효하다.
7. `now() >= expires_at` 이면 만료되어 쓸 수 없다.
8. **만료된 이후 다시 초대가 필요할 때만** 새 token 을 만든다.
9. 새 token 을 발급하면 **그 시점부터 다시 7일**을 준다.

### 4-2. 이 정책이 아닌 것 — 오해 방지

| ❌ 이런 뜻이 아니다 |
|---|
| 새 링크를 만들면 아직 유효한 기존 링크를 즉시 revoke 한다 |
| 초대 버튼을 누를 때마다 새 token 을 만든다 |
| 다른 멤버가 초대 버튼을 누르면 앞사람이 공유한 링크가 끊긴다 |

| ✅ 실제 의미 |
|---|
| 유효한 링크가 있는 동안 → **기존 링크 재사용** |
| 7일 경과 → `expires_at` 에 의해 **자연 만료** |
| 만료 후 다시 필요할 때 → **그때 새 링크 생성** |

### 4-3. 여행별 활성 링크 invariant

> **하나의 여행에는 동시에 쓰는 유효한 초대 링크가 하나다.**

```
파리 여행 → token X 발급 (7일)

  A 가 공유   → X
  B 가 공유   → X        같은 링크다
  C 가 공유   → X

  수신자 여러 명 → 모두 X 로 참가 신청 가능

7일 경과 → X 만료
그 이후 첫 초대 요청 → token Y 생성 → 다시 7일
```

## 5. 칼럼의 의미

### 5-1. `expires_at` 과 `revoked_at` 은 같은 것이 아니다

| 칼럼 | 의미 |
|---|---|
| `expires_at` | **정상적인 7일 만료 시각.** POL-INV-014 의 링크 갱신은 **전적으로 이 칼럼 기준**이다 |
| `revoked_at` | **POL-INV-014 의 정상 만료·갱신에는 사용하지 않는다.** 별도의 사용 정책은 아직 확정되지 않았다 |

**현재 POL-INV-014 구현은 "새 링크를 만들면서 기존 링크의 `revoked_at` 을 채운다" 를 전제하지 않는다.**

`revoked_at` 은 POL-INV-014 의 정상 만료·갱신에는 사용하지 않는다.
**현재 별도의 사용 정책은 확정되지 않았으며, 팀 합의 전까지 의미나 동작을 임의로 정의하지 않는다.**

칼럼 자체는 DB 담당자가 만들어 둔 스키마이므로 **지우거나 바꾸지 않는다.**

### 5-2. `created_by` 는 "마지막에 공유한 사람" 이 아니다

```
created_by = 그 invite/token 을 최초로 만든 사용자
```

유효한 링크 하나를 여러 멤버가 공유하므로 이 값으로 "누가 공유했는지" 를 추론하면 **틀린다.**

```
A 가 최초 생성            → created_by = A
B 가 유효기간 내 초대 실행 → 기존 링크 재사용 → created_by 는 A 그대로
```

**B 가 실제로 공유했다는 사실은 `created_by` 에 남지 않는다.**
공유 행위를 추적해야 한다면 별도 로그·이벤트 영역이고, 지금은 만들지 않는다.

## 6. 구현 요구사항 — get-or-create trip invite

향후 backend 구현자는 다음 동작을 만족해야 한다. **구현 방식(RPC / Edge Function)은 DB 담당자가 정한다.**

```
1. 그 trip 의 현재 유효 invite 를 조회한다
2. expires_at > (서버 기준 now) 인 invite 가 있으면
   → 기존 token 과 expires_at 을 그대로 돌려준다        ← 새로 만들지 않는다
3. 유효한 invite 가 없으면
   → 새 token 을 만든다
4. expires_at = (서버 기준 now) + 7 days
5. 새 invite 를 돌려준다
```

**만료 판정은 서버 시각 기준이다.** 기기 시각을 믿지 않는다.

> ⚠️ **동시성.** 여러 ACTIVE 멤버가 동시에 초대를 실행해도 **한 여행에 유효한 링크가 여러 개 생기면 안 된다.**
> §4-3 invariant 가 깨진다. DB/backend 에서 atomic 하게 처리해야 한다.

## 7. 함께 확정된 여행 초대 정책 요약

| 정책 | 값 |
|---|---|
| 사용자 기능으로서 모임 멤버 초대 | **없음** |
| 초대 대상 | group 이 아니라 **trip** |
| 링크 생성·공유 권한 | **현재 ACTIVE 여행 멤버 누구나** (여행장 전용 아님) |
| 링크 유효기간 | **7일** |
| 동일 링크 다인 사용 | **가능** |
| 유효기간 내 재실행 | **기존 링크 재사용** |
| 새 링크 생성 시점 | **만료 이후에만** |
| 링크 수신 즉시 멤버 | **아님** |
| 참여 확정 조건 | **참가 신청 → 여행장 승인** |
